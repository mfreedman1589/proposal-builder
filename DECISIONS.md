## Backend, data and fallbacks

### Supabase access, fallbacks and caching

- **All Supabase access goes through `db.py`, and every loader falls back rather than raising.** Nothing else imports the supabase client — one module owns the connection, so the fallback policy is enforceable in one place instead of at each call site. Every *read* returns `(value, warning)`: `value` is the real data when Supabase answered and the local fallback otherwise, `warning` is `None` on success and a plain-language sentence the caller shows with `st.warning` when it isn't. **A fallback is never silent, and a loader never raises for an unreachable backend** — the form has to render offline, on a broken URL, on a paused project, and in local dev with no secrets. *Writes* return `(ok, error)` instead: there's no local fallback for a write, but a failed one must not take a generated deck down with it (a failed `log_proposal` is a caption, not an error). A loader returns `None` rather than `[]` when the caller should fall back, because from the form's point of view an unreachable project and an empty table are the same thing. The client is memoized on `(url, key)` rather than `@st.cache_resource` specifically so that editing `secrets.toml` to break the URL takes effect on the next rerun — otherwise the fallback path can't be exercised without restarting the server. What falls back to what: master deck → the checked-in `.pptx`; rate card → `FALLBACK_PRODUCTS`/`FALLBACK_SPORT_CPM` in `app.py` (marked fallback-only — **edit rates in Supabase, not there**; they will drift and that's expected); audience catalog → parsing the brochure PDF, which is why that parser is still live code. Catalog reads are paged past PostgREST's 1000-row default, since a silently truncated catalog would drop real segments from the finder and from what the model may pick.

## Deck assembly and slide selection

### Total TV branding

- **Total TV drives the deck's branding on its own, with no extra toggle.** Total TV ON swaps the market's co-brand cover in for `client_title` and the market's Total TV template in for `proposal_template` (all plan options use it); OFF is byte-for-byte the previous behaviour. `broadcast_schedule_template:<market>` joins only once a Wide Orbit schedule has actually been imported — without one there's nothing to fill a grid with, so the master's static placeholder stays. Replacement is a **sweep in `build_presentation`, not an omission from `resolve_active_keys`**, for the same reason as the avails rule: it then holds however a slide got selected, and two covers or two plan templates in one deck would be both visible to the client and silently wrong (`personalize` finds the plan slide by token, so a second one takes the fill). Both markets' variants are swept unconditionally on top of that — a competitor station's branding in front of a client is the worst thing this deck can do, so it can't survive even a selection bug. **Three of the seven new slides resolve from their notes label ALONE**: the co-brand covers and the Total TV plan templates are text-identical to the standard slides they replace and to each other across markets, differing only by a logo image, so no text anchor can separate them — a merge that drops speaker notes collapses them back onto the standard slides silently. `tests/test_draft_regression.py` builds the merged deck itself (`_merged_master`) and re-applies the key labels after `copy_slide_into`, which doesn't carry a notes part across; that's how the variants are testable before the real deck upload.

### Total TV slides are station-branded

- **Total TV slides are station-branded, and the market picks the variant — including the schedule slide.** `total_tv` is the market-independent slide; `total_tv:dc` (WUSA) and `total_tv:harrisburg` (WPMT) are the branded ones, selected by `resolve_active_keys` from `selections["market"]`. This shipped broken and it's the shape of bug worth remembering: the WUSA9 *Broadcast TV Strategy* schedule slide was keyed plain `total_tv`, so it looked market-neutral and rode along everywhere — **every Harrisburg Total TV deck went out carrying a DC station's schedule** next to its own WPMT slide. Two branded slides in a Harrisburg deck is more visible to a client than almost anything else the app gets wrong. Fixed by retagging that slide `total_tv:dc` in its speaker notes (deck version 5); nothing in the code changed, because the mechanism was always right and only the label was wrong — which is exactly why `key:` labels live in the deck rather than in `slide_map.py`. **There is no FOX43/WPMT counterpart to that schedule slide**, so a Harrisburg Total TV deck is one slide shorter than a DC one until somebody authors it. Tier 1's `check_total_tv_by_market` asserts each market carries its own station and never the other's, in both directions.

### Sports viewership slides are opt-in

- **A sport contributes its package slide; the viewership chart is opt-in, and "absent" means the old behaviour.** Every selected sport used to pull a matched pair, so a four-sport proposal pulled nine slides where four were asked for. `products.live_sports.viewership` is one deck-wide checkbox covering every selected sport plus the `sports_viewership_intro` overview — deliberately **not** per sport, since a deck showing the stats for two of its four packages reads as an omission rather than a choice. The `sports` intro block is untouched by it. `sports.get("viewership", True)` is the one place a missing key means True: only a proposal logged before the toggle existed carries no flag, those were all built with the viewership slides in, and "Rebuild as presented" has to reproduce what the client received. The form always writes it explicitly through `read_products_selection`, so that default never governs a new proposal. Same shape as `vertical_attribution: None` below — when a new selection field changes what a *rebuild* produces, the legacy value has to be the old behaviour, not the new default.

### Vertical attribution (Polk Signals / Arrivalist)

- **Auto and travel sell their own attribution product, and it stands in for the generic line.** Polk Signals (automotive) and Arrivalist (travel) are named, branded measurement products; both slides rode into every deck for their vertical automatically, with no way to leave them out, while the Included-with-Campaign list said "Sales Attribution (CRM Upload Required)" — a different mechanism from either. `assembly.VERTICAL_ATTRIBUTION` holds both, and a checkbox in Section D (checked by default) drives the slide *and* the line. It is keyed to the **vertical alone**, not to the Sales attribution toggle beside it, and per-vertical (`vertical_attribution_auto` / `_travel`) rather than one shared key, or an answer given about Polk would carry over to a travel proposal. **Auto replaces the generic "Measure Sales Conversions" slide; travel doesn't** — Polk Signals *is* new-car sales attribution, so showing both says the same thing twice, while Arrivalist measures visits to a destination rather than closed sales and the generic slide still has something of its own to say. That asymmetry is the `replaces_sales_slide` flag and is not an oversight. Both slides carry their vertical's own condition_key (shared with its stats and precision-targeting slides), so they're matched by a **text marker** — each slide's own section footer, unique across master version 6 — and swept in `build_presentation`, the same mechanism and the same reasoning as `SCHEDULE_PLACEHOLDER_MARKER` and the Total TV variants. The replacement only fires when the branded slide is actually present, since with the vertical's slides switched off dropping the generic one would leave the deck with no sales attribution slide at all. **Known and deliberately left alone:** a travel deck also carries slide 31 ("Actionable OTT Reporting Insights"), near-identical Arrivalist copy keyed `vertical:travel` in the measurement section, which the checkbox does not control — it predates this and is a question about the master deck rather than about the code.

### Master deck optimisation and the size gate

- **A master deck is optimized on the way into storage, and blocked if it still won't fit.** `optimize_deck.py` re-encodes opaque PNGs as JPEG — the v1.1 master is ~95MiB, of which ~81MB is PNG, and almost none of that is resolution (nothing exceeds 2000px, half the images are under 220px); it's photographic content saved losslessly. That takes it to ~48MiB against a 50MiB storage ceiling. Images that *actually use* their alpha channel (checked pixel-wise — plenty carry a fully-opaque alpha they never use) stay PNG, since flattening them would fill every transparent pixel with black. Vector (`.emf`/`.svg`) and embedded fonts are untouched. Renaming a part to `.jpeg` means rewriting the relationships pointing at it: image references in slide XML are part-local rIds, so only the `.rels` files carry filenames — matched on the full basename with a boundary, because image names are prefixes of each other and a plain replace of `image33.png` would corrupt `image335.png` too. **The optimizer is idempotent and must stay that way**: existing JPEGs are left alone unless they need downscaling, because a deck round-trips repeatedly (download the active master, edit a slide, re-upload) and re-encoding cost a measured 0.0MB while still replacing 85 of 255 parts — pure quality erosion on every pass. Re-running it on its own output now produces a byte-identical file. `db.prepare_deck_for_upload` sits in front of every upload route: if the *optimized* deck still exceeds the limit, nothing is uploaded and no version row is written, so the active deck is untouched, and the error names both sizes and both ways out. Always verify a new build with `--verify`, which re-derives the slide map from both decks and fails unless every slide still resolves to the same `condition_key`.

### Nothing depends on slide numbering

- **No part of the app depends on slide numbering.** The "Standard" preset used to be a literal slide-number allowlist (`STANDARD_CORE_SLIDES = {1, 2, 3, 4, 5, 7, 13, 19, 21, 22, 118}`), which silently assumed the master deck's numbering never moved — it does, which is the entire premise of the deck update page, and that list would have mis-assembled every deck after the first update. It's now `CORE_CONTENT_KEYS` (`core:premium_content`, `core:attribution_overview`, `core:reporting`, `core:web_attribution`), selected by condition_key like everything else. Those four slides needed **new anchors of their own** in `slide_map.py`, because they previously fell through to the ambient `full_deck` default which eleven slides share and so can't single them out; "extended" now has to add `CORE_CONTENT_KEYS` alongside `full_deck` for the same reason. The old numbers decomposed as: 1/2/3/4/5 already covered by `client_title`/`campaign_specs`/`always`, 7/19/21/22 the four core slides, 13 the avails template (now `STANDARD_FORCED_KEYS`), 118 the "Proposal Slides" divider (dropped from every proposal anyway). Watch the anchor collisions: `"Transparent Reporting"` alone also appears in the Live Sports "Why Choose PREMION" copy and stole slide 68 on the first attempt — it's paired with `"DETAILED REPORTING"` now. Verified behaviour-neutral across 105 preset/vertical/toggle/product combinations, all keeping byte-identical slide sets.
- **"Standard" forces the avails template in even when the form's toggle is off** (`STANDARD_FORCED_KEYS`), preserved from the old allowlist's unconditional slide 13. Because of that, targeting/avails mutual exclusion is enforced as a **post-processing step in `build_presentation`** based on which slides actually ended up in `keep_numbers` (not on the toggle value alone) — this applies globally across all three presets: whenever the personalized avails template is present, the vertical's static Precision Targeting slide is dropped, full stop. (An earlier version of this note said the two slides could appear together under "Standard" — that was a real bug, fixed; don't reintroduce it by going back to toggle-only exclusion.)

### Section dividers

- **No section dividers appear in a generated proposal, ever.** All ten section-title cards ("Proposal Slides", "Live Sports", "Total TV", "Audience Marketplace", the three transitional ones, …) classify as the single `slide_map.SECTION_DIVIDER_KEY`, and `build_presentation` drops them. The exclusion is a **post-processing step that runs after the `STANDARD_CORE_SLIDES` union**, not merely an omission from `resolve_active_keys` — that allowlist is a literal slide-number list and contains slide 118, the "Proposal Slides" divider, so a key-based exclusion alone would let it back in under "standard" (exactly the shape of the older targeting/avails bug). Each `SECTION_DIVIDERS` entry still carries a carry-forward default, which matters even though the slide itself is dropped: the slides a divider *introduces* are resolved by it.

### Case study insert point, slide duplication and partnames

- **The case study insert point resolves by token, not by condition_key.** It matched `"proposal_template"` exactly, which stopped being the only plan slide when Total TV shipped its market variants (`proposal_template_total_tv:dc`) — nothing matched, the lookup fell through to appending at the end, and every Total TV proposal put its case studies *after* the media plan, where they argue for nothing. It now finds the slide carrying `{{PLAN_TITLE}}`, which is what makes a slide the plan slide and is how `personalize` finds it too; the key-based match is kept as a fallback and now covers `TOTAL_TV_PLAN_PREFIX`. Verified across standard, extended, quick pitch, Total TV DC and Total TV Harrisburg.

- **Case studies go immediately before the media plan slide, and the graft must happen before `personalize`.** Anchored to the plan slide itself rather than a divider, so it survives a deck without one. Two independent reasons the ordering matters: the plan slide is located by its `{{PLAN_TITLE}}` token, which `personalize` consumes; and `personalize` clones the plan slide once per extra option **directly after** the original, so inserting ahead of the original is what puts case studies before option A rather than between A and B. The divider fallback in `case_study_insert_index` is kept deliberately even though dividers are now always dropped — a future master deck that reintroduces one should degrade to "before the proposal section", not dump case studies after the plan. **Nothing is ever included silently:** vertical-matching case studies are pre-checked (3 most recent) but always visible and overridable, and off-vertical ones sit in an expander rather than being hidden. The pre-check works *because* a keyed checkbox's `session_state` entry beats its `value=` argument (the same convention documented above) — the default applies once and the seller's choice then sticks — but the `cs_pick_*` keys are deleted when the vertical changes, or they'd carry the previous vertical's answer.
- **Slide duplication is how multi-option decks are built, and rIds are the whole trick.** python-pptx has no slide-copy API. `assembly.duplicate_slide` adds a slide from the *same layout* (so inherited placeholders/theme match), deletes the placeholders `add_slide` auto-clones from that layout, then copies the source slide's shape tree across. The non-obvious part: shape XML references relationships (`r:embed` on pictures, `r:id`, `r:link`) that are **part-local**, so a naive deepcopy yields a slide whose pictures point at rIds meaning something different — or nothing — on the part they now live on. Each source relationship therefore gets an equivalent on the new part and every reference in the copied subtree is rewritten via `_remap_relationship_ids`. Two deliberate exclusions: the slide-layout rel (the new slide has its own) and the notes-slide rel (a notes slide belongs to exactly one slide; sharing one part between two slides is malformed). Clones are made **before** any `{{TOKEN}}` is consumed — each needs a pristine copy to fill — and positioned by removing the appended `<p:sldId>` and re-inserting it at the target index, the same manoeuvre `reorder_vertical_stats_slide` uses.
- **A duplicated slide needs a partname nobody else is using.** python-pptx names a new slide `slide{len(sldIdLst)+1}.xml`, which assumes slides are numbered contiguously from 1. After `build_presentation` has deleted most of the master that is false — the ~20–50 retained slides keep their original numbering out of a 119-slide deck, so the "next" name collides with a slide that still exists. **Nothing raises.** The only symptom at save time is a `zipfile` `UserWarning: Duplicate name: 'ppt/slides/slide54.xml'`, and one of the two parts silently overwrites the other, which shows up downstream as plan slides landing at non-consecutive positions, two options' totals on one slide, and other slides losing their fill entirely. `_next_free_slide_partname` scans the reachable parts and claims the lowest genuinely-free number *before* `add_slide` picks a colliding one. Note this class of bug is invisible to a synthetic test deck built from scratch, because its slides *are* contiguously numbered — it only appears against the real master.

## The media plan and the form

### A product toggle diffs the plan; stale state after a draft

- **A product toggle diffs the plan; it never rebuilds it.** The "product selections changed" branch used to reseed every option's rows from scratch, which meant ticking any Section C box — or importing a schedule — silently zeroed a drafted plan, allocations and negotiated CPMs included. It now diffs: rows are added only for newly-selected products, removed only for deselected ones, and **every existing row is left alone**, drafted or dirty or otherwise. `_seeded_tactics` records what the last selection produced so "deselected" is knowable; removal matches by prefix, since a drafted row appends its own label (`Premion Streaming TV — Commercial` belongs to `Premion Streaming TV`). Additions are guarded by what's actually on the grid rather than by that stored list, because a draft and a rehydration both write rows without it and appending blindly would duplicate every line. **This is the second time a rerun path silently zeroed drafted rows** (the first was the `_product_seed_key` mismatch), which is why `check_post_draft_edits` tests the whole seller sequence — draft, toggle on, import, toggle off — rather than any single step.

  **A keyed multiselect ignores `default=` once session_state holds a value**, which is how the flight label became "TBD": a draft sets new dates over whatever the form was showing, the months chosen for the *old* flight are all invalid against the new range, the selection filters to nothing, and `format_flight_label([])` returns "TBD". An empty intersection means the stored choice belongs to a different flight and the whole new range is reselected; a partial overlap is real custom flighting and is kept. Same class of bug as the option-name widget keys — anything whose `value=`/`default=` is computed from replaceable state.

  **FLOW_REWORK_PLAN.md Phase 2 (2026-08-27) replaced the multiselect itself** with per-month range controls (a checkbox plus editable dates, one row per month) — the multiselect could only drop a whole month, never clip one to part of its span. The reconciliation rule this incident produced didn't change, only where it lives: `flight_month_ranges` is now the single owner (`form_flight_months` and `main()`'s own inline copy both collapse onto it), and the same empty-intersection-resets / partial-overlap-keeps behavior applies to per-month *ranges* now, not just whole-month labels. The ordinary widget-key generation-bump discipline (`bump_flight_months_generation`, on the month *set* changing, not on an edit to one month's own range) is the per-month-control's own version of the `value=`-ignored trap.

  **And the sibling that guard doesn't catch: a rule that only discards stored state on *zero* overlap silently keeps a stale subset when the old and new states partly agree.** The empty-intersection reset above fires on a clean break and does nothing on a partial one, which is the commoner case — the form opens on Sep–Nov, a draft sets Oct–Dec, two months are still valid, so the stored selection survives filtered down to `[Oct, Nov]`. The draft had already spread a $45,000 budget over its own three months, `main()` then totalled it over two, and the deck went out reading `Full Flight Total (2 months)  $30,400` with the $1,200 production fee divided $600/month instead of $400 — while the Flight column and Campaign Specs, drafted and dirty and so never re-seeded, still said Oct–Dec. The fix is not a smarter overlap rule: **whoever replaces the state owns all of it**, so `apply_draft_to_form` writes `active_months` outright (as `rehydrate_proposal_into_form` always did), and where it has no say over the flight — no usable dates, or a `flight` section the clarify round is skipping — it reads the form's months via `form_flight_months()` rather than assuming one. The flight widget defaults are constants (`DEFAULT_FLIGHT_START`/`_END`) precisely so that helper can predict what the widgets will do before they render. Generalise it: *partial* agreement between old and new state is the case a staleness guard has to be tested against, because zero-overlap and total-overlap both look correct. `check_drafted_months_survive_a_used_form` reproduces it, and `check_budget_ties` asserts the invariant that makes it visible at all — the month count that spreads a budget must be the one that totals it, names itself in the totals row, and divides a flat fee. Tier 1 missed it for as long as it did for two reasons worth separating: `n_months_of()` recomputed the count from the draft's own flight dates (see the self-consistent-check note below — it is one of the four instances), and `apply_draft()` only ever ran against an empty session, when a draft landing on a form the seller had already been working in is the case that breaks.

  **FLOW_REWORK_PLAN.md Phase 5 (2026-08-30) removed the code this whole incident lived in, rather than reconciling it more carefully.** Market, flight dates and plan basis became band *inputs* to drafting instead of drafted *outputs* — `apply_draft_to_form` no longer writes `market_choice`, `flight_start`, `flight_end` or `active_months` at all (the schema fields are gone too, so the model is never even asked), and reads them from `st.session_state` as already-given context instead. There is consequently no longer a second, drafted flight for the form's own flight to disagree with — **the incident above is now structurally impossible, not merely guarded against.** The reconciliation branch this paragraph documents (the `if flight_start and flight_end and "flight" not in skip_sections:` path) was deleted outright rather than left as dead code; `apply_draft_to_form` unconditionally takes what used to be its `else` branch, reading the form's own flight via `form_flight_months()` exactly as `rehydrate_proposal_into_form` always did. **A same-shape bug was found and fixed alongside it**: `avails_basis` (the Monthly/Full-Flight plan-basis toggle) was being force-written to `AVAILS_BASIS_MONTHLY` unconditionally whenever drafting built its own avails rows, silently overwriting whatever the rep had picked in the band — same root cause (a drafted value competing with a band value that should have sole ownership), same fix (delete the write, read the band's own value instead). Because a migration that merely preseeds every Tier 1 fixture's *own* flight/market as the band preset would stay green whether or not the removal actually worked (the preset and the fixture always agree), `check_drafted_months_survive_a_used_form` was replaced with `check_band_flight_survives_a_disagreeing_draft` — the band is preset to one flight, the draft dict still carries a *different* one (simulating a frozen legacy fixture or an off-schema model response), and the band's own flight must survive untouched. That is the test that actually proves the write is gone, not just that nothing currently disagrees with it. The contradiction rule — a notes date/market/basis that disagrees with the band never overwrites it — is enforced by the schema's absence now, not a runtime check: there is no field left for the model to return one in.

### The avails table is research; targeting groups own their Premion Streaming TV line

- **Three separate mechanisms used to create a group's plan line, and they disagreed with each other.** `queue_group_seed`/`seed_pending_group_rows` gave a freshly-imported or hand-built group its own line automatically; `apply_draft_to_form` invented its own `media_plan_lines` from the model's `audiences[]` and — the real bug — **overwrote `targeting_groups` wholesale** the moment any audience was drafted, even when a real avails import had already resolved a group's `geo_def`/`resolved_zips`/`resolved_markets`. Import-then-draft silently destroyed the import; draft-then-import produced two disconnected group sets sitting side by side. Both are symptoms of the same missing decision: nobody owned "does this group have a plan line," so three different call sites each answered it their own way.

- **The fix is an explicit, owned boolean, not a smarter heuristic.** `include_in_plan` (default `False` on every group, however it was created) plus `include_locked` (same shape as `color_locked` — a rep, or a confirmed pre-selection, made a real decision; nothing automatic may change it again) are the single source of truth for whether a group contributes a Premion Streaming TV row. `reconcile_group_plan_lines` is the one function that reads it and reconciles the plan — called exactly once per run, after the ordinary product-toggle branches, and **idempotent**: run it twice with nothing changed and nothing moves. That idempotence is not incidental — it's what lets import, draft and a later import all funnel through the same function and converge on the same end state regardless of order, instead of each needing to know what the others already did.

- **Premion Streaming TV had to be fully carved out of the existing product-toggle diff (`_apply_product_diff`) rather than taught to respect `include_in_plan`.** That diff removes a deselected product's rows **regardless of `dirty`** — correct for retargeting/AM/sports (a rep who un-ticks a product clearly wants its rows gone, edited or not), and exactly wrong for a group row, where an edited line must never be discarded without a confirmation naming the numbers. Teaching one function two different removal policies keyed on row type was rejected as fragile; giving Premion Streaming TV a completely separate owner (the reconciler) that the diff never touches at all is simpler and can't regress the other products by accident. `_seed_option_rows` passes a copy of the selections with `_premion_streaming_tv` forced off, so `_seeded_tactics` never contains that tactic and the diff structurally cannot add or remove a group's row.

- **The uncheck-with-edits confirmation went through two designs.** The first had the Remove/Keep buttons read `_pending_include_removal`, mutate state, and call `st.rerun()` directly inside their own `if st.button(...)` block — mirroring how the buttons were first written. It failed in testing: the D2 fold-back (which runs earlier in the same script, above the buttons) reads that same key on ITS render and, finding nothing to add (`pending_blocked` empty that render), leaves it untouched rather than clearing it — so a button that both reads and writes it in one pass has its write immediately shadowed by the fold-back's own stale copy on the very next render. Moved onto the SAME queue-then-apply-before-D2-reads-groups shape `apply_pending_color_cascade` already used (`apply_pending_include_confirm`, called alongside the other three D2 appliers before `sync_targeting_groups`) — one mechanism for every D2 bulk/confirm action, not two. Caught by `tests/test_group_plan_selection.py`'s Keep/Remove flow going red before the move, not by inspection.

- **Retargeting/AM/sports/fees stopped fanning out one row per targeting group in the same pass, and this was a discovered scope expansion, not the original ask.** They inherited the fan-out purely from sharing `_seed_option_rows`/`seed_media_plan_rows` with Premion, which used to pass the per-group `plan_lines` as `geo_default` for every enabled product uniformly. Once Premion Streaming TV is carved out into its own owner, there is no remaining reason for the other products to fan out at all — they were never conceptually "one line per targeting group," and a 12-group avails table with Retargeting on used to produce 12 Retargeting rows regardless of how many of those 12 groups were actually selected into the CTV plan, directly contradicting "the avails table is research." Fixed by passing the single flat `default_geo` instead of `plan_lines` for every product except Premion — one Retargeting/AM/sports/fee line per campaign, exactly as it worked before targeting groups existed.

- **Backward compatibility is an asymmetric default, not a migration script, same shape as `sports.get("viewership", True)`.** A group logged before `include_in_plan` existed has no such key; on a LOADED proposal, missing means "whatever its rows already say" (derived from whether the group's id appears in any stored row's `_group_ids`, then locked) — a new-group default of `False` would silently drop every line off an old proposal's plan on reload. A proposal old enough to predate `targeting_groups` entirely (flat `avails_seed_rows` only) migrates every group to `include_in_plan=True`: before groups existed, every avails row drove a plan line automatically, so that's the historically faithful legacy value, not today's opt-in default. Both are implemented exactly once, in `rehydrate_proposal_into_form`, never as a blanket `.get(key, True)` scattered across call sites.

- **Drafting's `group_selection`/`group_allocation` schema is gated on real groups existing at PROMPT-BUILD time, not just at apply time, and that gate has a known, accepted edge.** The prompt only lists existing groups — and therefore only asks the model to select from them — when `build_draft_prompt`'s `existing_groups` parameter is non-empty; a no-groups draft's prompt is byte-identical to before, which is what keeps every frozen tier-1 `.draft.json` fixture passing unchanged. The corollary: a draft run before ANY avails work exists is never even asked about selection and takes the old invent-Premion-lines-from-notes path, and nothing retroactively reshapes those invented lines once a real avails table shows up later — full convergence between "import-then-draft" and "draft-with-zero-groups-then-import" isn't achievable without asking the model about a table it's never seen, which was considered and rejected: the normal workflow already pulls avails before drafting (confirmed with the user), so this is a rep working out of order, not a case worth a prompt redesign or a rebuild-and-carry mechanism. `apply_draft_plan_intent_to_new_groups` still names the gap plainly (an `unresolved_internal` note) when a later import lands with no stored intent to apply and a draft already ran. The **narrower** convergence that IS guaranteed and tested (`tests/test_group_plan_order_invariance.py`): once real groups exist by the time selection is expressed, import-then-draft and draft-then-(a later)import reach the identical selected-groups/lines/amounts end state, because `draft_plan_intent` stores the model's **raw** selection criteria (`ids`/`match`/`mode`), not resolved ids — a stale id from a first batch would never match a second, unrelated one, but a `match` phrase or "select everything" both correctly re-resolve against whatever groups exist when `apply_draft_plan_intent_to_new_groups` re-runs the matcher later.

### The Targeting column carries the whole audience stack

- **The Targeting column carries the whole audience stack, and is per line.** An audience is normally defined by several attributes at once, so `audience_stack()` joins *every* Campaign Specs Audience bullet into a row's Targeting; `first_line()` printed one attribute beside a specs slide listing four (the Capital Ridge case). Silent truncation is the worse of the two available failures — an over-full cell is visible and a rep trims it, a missing attribute looks like a deliberate choice. Geography still uses `first_line()`: the Geo column is one market, not a stack. **But the audience stack is a per-line-type default, not a global one, and treating it as global shipped a regression.** `resolve_row_defaults` now resolves Targeting three ways: (1) the product's own `targeting_copy` from the rate card when it has one (Streaming Retargeting, every Live Sports package); (2) **the row's own copy, kept**, for the imported broadcast line, whose Targeting is derived from the Wide Orbit schedule (commercial count, programs/dayparts, cadence) and cannot be reproduced from a static string — broadcast is bought by program and daypart, not by audience segment; (3) otherwise the audience stack. Without (2) any shared-field edit re-seeded the clean broadcast row and a demo deck went out with that line reading "Homeowners with higher household income (100K+)…". **Its Geo is held by the same rule and is the more dangerous half**: that value comes from the station's call sign (WUSA → Washington DC DMA) and is deliberately never guessed, so re-seeding it from the form's market would put a wrong DMA on a client's media plan whenever station and market disagree. `tests/test_broadcast_e2e.py` makes the edit rather than reading the freshly seeded row — the edit is what triggers it — and asserts a *streaming* line did take the new stack, so the broadcast row holding still can't pass because the edit never landed. **Audience Marketplace was reviewed at the same time:** Audience Targeting correctly takes the stack (it really is audience segments), while **Geofencing** (bought by fence) and **Site Retargeting** (visitors, exactly the case Streaming Retargeting already has copy for) both want their own. That needs no code — `targeting_copy` is a per-row column on the `products` table, so it is a data edit in Supabase, and the copy is client-facing wording that should come from Premion rather than be invented here. All three call sites (`main`, the draft path, the rehydration path) must change together, since `default_targeting` feeds `_shared_fields_key` and a mismatch re-seeds the grid. The drafting prompt states the matching rule from the other end — **separate audiences sharing a budget get separate lines** (signal: an explicit split, or tracks the client names as distinct), **one audience described by several attributes stays one line**, several audiences with no split stated get a line each with `split_evenly` and a flagged assumption, and a genuine ambiguity is resolved to the best-supported reading and named in `unresolved`. Tier 2 tests both halves adjacently (`ashford_two_track` / `capital_ridge_stacked`) because either alone can be satisfied by always splitting or never splitting. Layout holds, but **the column widths depend on which plan template is in play and that difference hid a real bug**: on the standard six-column plan slide Targeting is the widest column at 3.30in and a four-attribute stack wraps to two lines at 10–12pt, which `condense_media_plan_table` reserves per row (verified 1/5/9/12 rows, +0.25in clearance throughout). On the **Total TV** plan slide the table carries a seventh column and Targeting is only **2.12in**, so every cell in a row wraps and the same stack takes three lines. Quote 3.30in as "the Targeting width" and you are describing one of the two templates; the narrower one is where a measurement error shows up first, because everything there is already near a wrap boundary.

### Options, bidirectional cost/impressions, row types, audiences

- **A proposal carries 1–3 media plan options, and one option must render exactly like no options at all.** `fill_data["media_plan_options"]` is a list; `assembly.personalize` clones the plan template once per extra option and fills each independently. Because each option's title and totals differ, the plan's own scalar tokens (`PLAN_TITLE`, `TOTALS_LABEL`, `TOTAL_IMPRESSIONS`, `TOTAL_COST`) moved **out** of the deck-wide `fill_all_simple_tokens` pass into a per-slide `_fill_simple_tokens_in_slide` — leaving them in the global pass would stamp option A's numbers onto every option's slide. The option name is appended to the plan title *only* when there's more than one option (`option_plan_title`), so a single-option deck has no "Option A" label anywhere and is byte-for-byte what it always was. In `app.py` each option owns its name, rows, per-row dirty/driver lists, breakout mode and editor version (`new_plan_option`); a new option can clone an existing one (`copy_plan_option`), and clones start **dirty** so the shared-field re-seed can't quietly undo a deliberate copy.
- **Impressions and Cost are bidirectional, resolved by a per-row driver flag.** The media plan grid takes either side: `media_plan_driver` records which one the user last typed into, and `recompute_row` derives the other from it (`cost_from_impressions` / `impressions_from_cost`, an exact matched pair). A **CPM edit deliberately does not change the driver** — it re-derives the other side from whichever is already driving, which is the case that needs the tracking at all. The reconcile pass bumps the editor version and reruns once when it actually changed a value; that guard is what stops an infinite rerun loop, since on the next pass every row already matches its own derivation. Drafted rows drive from **cost** — the allocation amounts are already group-rounded to tie to the budget, so deriving impressions from them preserves the total, where deriving cost from rounded impressions would reintroduce drift. The preview and the deck read `Cost` straight off the row rather than recomputing it, which is what makes the grid, the totals and the generated slide tie exactly. **(FLOW_REWORK_PLAN.md Phase 4b removed the markup term from this pair entirely** — see "The agency gross-up rebuild" below; a row's Cost/Impressions relationship no longer has anything to do with the agency checkbox.)
- **A media-plan row can be Rate (impressions × CPM) or Flat Fee — a UI-level distinction, not just a drafting one.** Any row's `Type` column can be set to "Flat Fee" (independent of whether it came from a draft): Impressions/CPM are ignored and the row's cost is its `Cost` value directly — no markup, and **not** scaled by month count, since a one-time fee isn't a recurring rate. (`Cost` subsumed the old separate `Flat Cost` column when the grid became bidirectional — one money column that means "what this row costs" for both row types, rather than two adjacent ones where only one ever applied.) That "not scaled" requirement exposed a real pre-existing bug: the full-flight total used to be computed as `monthly_total_cost * n_months`, which is only correct if every row scales linearly with month count — a flat fee doesn't, so that shortcut would have silently over-counted it by the number of active months. Fixed by accumulating each row's own `full_flight_cost`/`full_flight_impressions` directly instead of deriving the totals from the monthly ones. `assembly.py` needed **no changes** for flat-fee rendering — its table fill is plain per-cell token-string replacement, so passing `"--"` for a flat-fee row's impressions renders exactly like any other string value would.
- **Audiences are vertical-independent.** Section D2 (avails table + Audience finder) and the "Include personalized targeting / avails table" toggle used to be gated behind a selected vertical, which left a no-vertical proposal with no route to the catalog at all. The avails template is keyed off its own toggle alone now; a vertical only supplies the *fallback* (its own static Precision Targeting slide) for when that toggle is off, and with no vertical there's simply no fallback and neither slide appears. Throughout the finder a vertical **prioritizes, never filters**: browse sorts vertical-relevant categories to the front via `prioritize_catalog` (nothing is removed), and suggest mode uses the form's vertical only as a fallback hint when the typed description doesn't imply one. With no hint at all `build_catalog_slice` sends the **full** catalog rather than a top-150 cut — the cap is a relevance-preserving economy only when there's a hint to sort by; without one it would drop segments arbitrarily.
- **One custom (non-RFP-selectable) audience per campaign, enforced but never silently.** Checked directly against the D2 avails table itself (catches manual edits, "Audience finder" browse/suggest adds, and AI-drafted audiences alike, regardless of source) and, in Suggest mode, against a recommendation set specifically before any of it gets added — both show a visible `st.warning` rather than dropping anything on your behalf. **The draft path is the exception, and caps structurally rather than warning**: `apply_draft_to_form` keeps the first custom segment and moves the rest into `unresolved` as named, swappable alternatives. The prompt asks for at most one too and that guidance is worth keeping — it makes the first pass better, and the survivor is then whichever segment the model ranked highest — but a prompt instruction is a probability, not a guarantee: the same dental notes returned one custom segment on one live run and two on the next, which is what moved the limit into Python. Tier 1's `custom_audience_cap` scenario feeds in a deliberately non-compliant draft (three customs plus one selectable) and asserts exactly one survives, so this is testable offline instead of riding on a probabilistic live run. Tier 2 still checks the unaided first pass, but as a prompt-quality signal rather than a correctness gate.

### A Monthly-breakout option's full-flight total is live, not stored — pre-existing bug, found and fixed during the Phase 1 setup band

- **A Monthly-breakout row's stored Cost is the rate the rep typed; `compute_plan_totals` DERIVES the option's Full Flight Total by multiplying that rate by `n_months`.** (A Full-Flight-breakout row is the opposite and the safe one: its stored Cost IS the full-flight figure directly, monthly derived by dividing — immune to a flight-length change by construction.) This has always been true, on every proposal that has ever existed — Phase 1 didn't create it, it only moved the flight-date widgets from the bottom of the page to the top, which is what actually surfaced it as something worth fixing now rather than later: once `flight_start`/`flight_end` sit in a persistent band a rep can revisit mid-session, editing them after pricing a Monthly-breakout line has become an ordinary, expected action rather than an edge case, and every existing dirty-row protection (`_apply_product_diff`, the shared-fields-key reseed) is about protecting a ROW's own Cost/Impressions from being overwritten — none of them were ever positioned to catch a *derived total* moving out from under an unchanged row.

- **The obvious first design — freeze `n_months` at its old value until the rep confirms a "Recompute totals?" prompt — was proposed and rejected.** It would leave the band's own displayed flight dates and the plan's actually-priced month count silently disagreeing with each other for as long as the rep didn't answer the prompt: exactly the kind of two-live-values-for-one-fact split this whole rework exists to end (see the plan's own principle 1, "one computation feeds every surface"). Worse, a rep who didn't notice the banner and clicked Generate anyway would ship a deck whose displayed flight and whose quoted total told two different stories — a strictly worse failure than a consistent deck at a total nobody meant to ship. If this gets proposed again (freezing is the intuitive shape for a "confirm before changing" gate, and it will keep looking that way to a future reader who hasn't traced `compute_plan_totals` first): dates change, the total that depends on them follows immediately and without exception, and the guard's whole job is to make sure the total's move is *seen*, not to make it *not happen*.

- **The guard is keyed on `(flight_label, n_months)` — the same two values `main()` already derives from `active_months` — never on the band's raw `flight_start`/`flight_end`.** Widening `flight_end` alone does not widen `n_months`: the per-month control (originally a keyed multiselect; see FLOW_REWORK_PLAN.md Phase 2 above) keeps a still-valid partial selection rather than auto-growing it (the documented "partial overlap is kept" rule, same section above), so a rep who only drags the end date out further has changed nothing about what's priced until they also add the new months as active. A raw-date comparison misses that expansion case entirely and, in the other direction, would have flagged date edits that never touched a priced dollar figure at all. Keying on the derived values instead of the raw inputs means the guard is automatically right about *whether* a dollar total moved; it never needs its own copy of the reasoning `n_months`/`active_months` already encode. (Editing one month's own *range*, without changing the month set, is a separate case the per-month control introduced — the guard doesn't fire for it either, correctly, since a Monthly total is `monthly × n_months` and genuinely doesn't move when only a range's clipping changes.)

- **Warns, blocks Generate, and requires a dismiss click — not a bare `st.warning`.** A banner that just sits there and quietly recomputes underneath itself is exactly as easy to miss as the silent version it replaces; naming both the old and new dollar totals (not just the flight dates, which describe the cause but not the consequence) is what makes the banner readable as "this is what changed" rather than "something about dates changed." Only fires for a Monthly-breakout option carrying a dirty row with nonzero Cost — a freshly-seeded $0 row, a Full-Flight-breakout option, or an untouched clean row all have nothing for a rep to have priced and lose track of. Guard: `tests/test_flight_change_guard.py`.

### The agency gross-up rebuild (FLOW_REWORK_PLAN.md Phase 4b) — the double-gross bug, and why the fix is "grossed exactly once, by the checkbox"

- **The incident: a live draft's CPM rendered at $41.40 = $36 × 1.15.** The old `agency_involved` toggle lived in Section A, was set by the drafting model itself (classifying notes as gross-vs-net commission language), and was separately applied by Python (`cost_from_impressions`/`impressions_from_cost` grossing a row's stored Cost, `compute_plan_totals` separately grossing the *displayed* CPM). Nothing stopped the model from already having reasoned about gross/net and written a pre-grossed rate, with Python then grossing it a second time on top. The toggle's own classification logic (CLAUDE.md used to carry a whole paragraph on when to read notes as "an agency is taking a commission" vs. "keep rates net") was itself the failure surface — a probabilistic read of ambiguous phrasing, multiplied into a client-facing dollar figure.

- **The fix is not "make the model classify better."** The rule that ends the whole class of bug: **a number gets grossed exactly once, by whoever grossed it first.** The model never grosses anything and never touches the checkbox — it transcribes whatever rate the notes state, verbatim, even when the notes explicitly say to gross it up ("the net CPM is $32, gross it up" → the model still writes 32). Grossing happens in exactly one place, `compute_plan_totals`, applied once via `row_markup`, at display/deck time, never on a stored row. `cost_from_impressions`/`impressions_from_cost`/`recompute_row`/`merge_plan_rows` lost their `markup` parameter entirely — there is no longer a *code path* capable of grossing a row twice, which is a stronger guarantee than "the prompt says not to."

- **A per-line gross-up rejected in favor of the settled business rule: gross-up is always order-wide.** The obvious-looking alternative — let the model gross a single line when the notes say so, independent of the rep's checkbox — was proposed and rejected during design. It re-opens the exact collision that motivated the fix: a line the model already grossed renders correctly with the checkbox off, but the moment a rep ticks the box for the REST of the order, that one line gets grossed a second time, since nothing on the row marks it as already-gross. Confirmed directly (not assumed): "there is no scenario where one Premion line grosses and another doesn't" — broadcast is the only exemption, and it's structural (`BROADCAST_EXCLUDED_FROM_AGENCY_MARKUP`), not a per-line flag. That single business fact is what makes the simple version correct: no marker column, no per-row exemption state, no case where the checkbox's own scope has to be reasoned about per line.

- **The avails-PDF importer's old auto-tick (from a document's Agency field) was retired for the same reason, not merely for consistency.** `_avails_import_field`'s `is_stated` parameter existed solely to let a document correctly saying "Direct - No Agency" apply or conflict as a real `False` rather than reading as "nothing stated" — real, load-bearing machinery for a single caller. Once that caller (`agency_involved`) was removed, the parameter had no other use and was removed with it rather than left as dead generality. An agency named in a document is now surfaced as an `unresolved_internal` note ("tick the gross-up checkbox if a commission applies") — a document field is a stated fact, unlike notes phrasing, but the checkbox stays a rep action regardless of source.

- **Migration for a proposal logged before this shipped is a real, silent-corruption hazard if skipped.** An old proposal with `agency_involved=True` has **gross** `Cost` stored on every non-broadcast rate row (the old system's storage-time grossing). Under the new system the grid holds net and grossing happens at display time — loading that proposal unchanged would tick the new checkbox (from the stored `markup == 1.15`) and gross an already-gross number a second time. `rehydrate_proposal_into_form` detects this by the *absence* of the new `form_json["agency_gross_up"]` key (present only on a proposal logged after this phase) and, only then, divides each restored non-flat-fee, non-broadcast row's Cost by 1.15 once before it reaches session_state. Impressions need no correction either way — they were computed from net cost/CPM under the old system too (impressions never carried markup), so the round-trip is exact.

### total_budget_basis — a gross-stated campaign budget, found from a real Capital Media proposal

- **The gap: Phase 4b taught the model to transcribe a gross-stated CPM verbatim, but never taught it — or Python — anything about a gross-stated BUDGET.** A live proposal's notes read "$15K total gross budget... net CPM is $32 and needs to be grossed up." The model did exactly what Phase 4b asks: wrote `total_budget: 15000` and `cpm: 32`, both transcribed verbatim, no arithmetic. But `resolve_drafted_lines` had no concept that a budget could be anything but net — it stored $15,000 directly as the row's net `Cost`, priced 468,750 impressions off it, and ticking the gross-up checkbox multiplied the already-gross-sized $15,000 by 1.15 to $17,250: a budget the client never agreed to. Root cause traced to `resolve_drafted_lines`'s Stage 1 (`amt = ... total_budget`, `app.py`) — not to `compute_plan_totals`/`row_markup`, whose per-line grossing (cost and CPM scaled, impressions untouched) was already exactly correct, and needed no change at all once fed the right net figure.

- **Two blanket fixes were considered and rejected before landing on a narrow field.** (1) *Always* divide any drafted `total_budget` by 1.15 before storage: breaks the overwhelmingly common no-agency case, where a plain "$50K plan" would silently store $43,478 and, with the checkbox off (a no-op multiply), never gross back up — the deck would show less than the notes said for every ordinary proposal. (2) Divide by the checkbox's *current* session_state value at resolution time: architecturally incompatible with Phase 4b's own settled principle that the checkbox never touches a stored row, and the checkbox's value isn't even decided yet at draft time in the normal workflow (draft first, decide gross-up after). Neither survives contact with the rest of the design.

- **The fix: `total_budget_basis` ("net"/"gross") mirrors `audiences[].avails_basis` exactly — notes state which convention a number is given in, Python converts, default preserves every existing draft byte-for-byte.** `_drafted_budget_basis` (app.py, beside `_drafted_breakout`) defaults to `"net"`; only a literal `"gross"` in the model's own output triggers anything. `drafted_options()` carries it with the same per-option-falls-back-to-top-level rule `total_budget` and `breakout` already use. The one arithmetic step it authorizes lives at the very top of `apply_draft_to_form`'s per-option loop, before the $0-budget check or `resolve_drafted_lines` ever run: `opt_in["total_budget"] = round(gross_budget_stated / AGENCY_MARKUP)` — a single named constant (`AGENCY_MARKUP = 1.15`, replacing the bare-literal `markup = 1.15 if agency_gross_up else 1.0`) shared with `compute_plan_totals`'s own multiply, so the divide-then-multiply round-trip lands exactly back on the stated gross figure by construction, not by coincidence.

- **Why this doesn't reopen the `agency_involved` incident, despite superficially looking like "the model classifies gross vs. net again."** The old classifier inferred *whether an agency commission applied at all* from ambiguous prose, and the model itself decided whether to write a pre-grossed number — a fuzzy business judgment feeding directly into arithmetic the model was trusted to have already done correctly. `total_budget_basis` asks something much narrower: did the notes use an *explicit label* ("total gross budget," "the client's all-in number," "includes our commission") for a number the model is transcribing anyway? The model still does zero arithmetic either way — Python's divide is the only computation, gated on a literal string match, not a judgment call. And the prompt states the escape hatch identically to the old incident's own lesson: an agency/commission mentioned with no indication which side of it the budget sits on stays `"net"` — guessing is explicitly the wrong move, the same conclusion that shut down `agency_involved`.

- **The checkbox is auto-ticked, not just flagged — a deliberate change from the first design.** The original plan (this file, above) called for a loud `unresolved_internal` note and nothing else, matching "grossing up is a rep action, the model never touches the checkbox." Overridden on request: leaving the checkbox off after a confirmed gross-budget conversion shows the rep a number nobody asked for (the net figure) on every such proposal, correctable only by remembering to tick a box the draft already knows should be ticked. The distinction that keeps this from re-opening Phase 4b's rule: **the model still never grosses anything and never touches the checkbox** — it transcribes a label. `apply_draft_to_form` (Python, deterministic, gated on the literal string `"gross"`) is what ticks it, exactly the same authority Python already has to write `total_tv`, `plan_options`, `live_sports_enabled` and everything else in `updates`. One click undoes it, same as any other drafted default. `agency_gross_up` was added to `DRAFT_KEY_SECTIONS` as `"media_plan"` so a re-draft that's preserving the rep's own hand-edits to the plan (`skip_sections`) leaves this alone too, rather than silently re-ticking a box the rep may have deliberately unticked.

- **Verified clean against the write-after-render hazard that bit `client_name` and `total_tv` before `BAND_WIDGET_KEYS` existed.** The risk that mattered here: does anything write `st.session_state["agency_gross_up"]` after that key's own widget has already rendered in the same script pass? Checked directly, not assumed: the checkbox lives in Section E ("beside the plan table near Generate"), which renders well after the Draft button's own call site in the script (the button sits in the setup band, at the top); `agency_gross_up` is confirmed absent from `BAND_WIDGET_KEYS` (the exact set that forces a write through the deferred `_draft_pending_fields` queue instead of a direct one); and the direct write happens through the same unconditional `st.session_state[key] = value` loop every other Section-E-owned field (`plan_options`, `show_sov`) already uses safely. No new mechanism needed, and none of the three existing safety rails (BAND_WIDGET_KEYS, the deferred-write queue, DRAFT_KEY_SECTIONS) had to change shape to accommodate this — only gain one more entry each.

### A drafted plan permanently opted out of the band's Breakout mirror — found from the same Capital Media session

- **The incident: add avails, draft from notes, switch the band's Plan basis Monthly → Full flight. The avails table converted; the plan didn't.** `test_breakout_band_sync.py` (2026-08-28) had already fixed the *general* version of this — an option that hasn't been locked (`option_breakout_locked`) re-syncs to the band's current default every render it's found diverged from it, so flipping the band after the fact moves an existing, untouched option. But `apply_draft_to_form`'s own `new_plan_option(..., breakout_locked=True)` call locked **every** drafted option unconditionally, the moment ANY draft ran — permanently opting it out of that mirror regardless of whether the notes said anything about presentation at all.

- **Root cause: two different things were being written to the same flag.** `option_breakout_locked=True` is supposed to mean "a human (or the notes) made a deliberate, informed choice about how this plan presents — never silently override it." But `drafted_options()`'s own breakout resolution (`_drafted_breakout`, fallback `BREAKOUT_MONTHLY`) hands back "monthly" for the overwhelming majority of real notes, which never mention presentation at all — that's a **default filling a gap**, not a decision, and it was being locked in exactly as hard as a notes-line that explicitly says "show it as one combined flight total." The rep's own Breakout radio widget already had the right test for this (`option["breakout"] != pre_widget_breakout` — did this genuinely change from what was already there) and drafting had no equivalent.

- **The fix applies the same test drafting should have used from the start.** `band_default_breakout = default_breakout_for_basis(st.session_state.get("avails_basis"))` — what a brand-new, untouched option would get right now, computed once before the per-option loop (reading the band's own `avails_basis`, which per Phase 5 is always already set by the time drafting runs). `new_plan_option(..., breakout_locked=(breakout != band_default_breakout))`: a draft that lands on the same value the band would have given anyway stays **unlocked** and keeps mirroring; a draft that names a genuine, different presentation (the notes actually said something) still locks, unchanged from before. `rehydrate_proposal_into_form`'s own `breakout_locked=True` (restoring a stored, already-finalized historical proposal) is untouched — that one is correctly unconditional, since an old proposal's breakout is a fact about what already shipped, not a fresh default.

- **Guard:** `tests/test_breakout_band_sync.py`'s `test_drafted_default_breakout_follows_a_later_band_flip` (the exact repro: draft at the band's own default, flip the band, the plan follows) and `test_drafted_explicit_breakout_still_locks` (the case that must NOT change: a draft that genuinely diverges from the band still locks and survives a later flip) — both run the real `apply_draft_to_form` via `test_draft_regression.py`'s `apply_draft` stub, then a real `AppTest` to flip the band's own radio widget, the same two-stage proof `test_breakout_band_sync.py`'s existing tests already use.

## Broadcast and Wide Orbit

### Broadcast lines are gross and never marked up

- **Broadcast lines are always gross and never marked up — settled, not a default.** A Wide Orbit cost is already gross: the station quotes it that way and the agency commission sits inside it, as the Planner PDF's own "Total Cost / Agency Commission @ 15% / Net Cost" block shows. Running the ×1.15 over it would bill the commission twice, so `BROADCAST_EXCLUDED_FROM_AGENCY_MARKUP` holds the row at markup 1.0 **regardless of the agency toggle**, and the grid carries a caption saying so. Enforced in `row_markup`, called from `recompute_row` — the single place markup touches a rate row, since `compute_plan_totals` reads Cost straight off the row. Recognition is by tactic name (`BROADCAST_TACTIC_MARKER`), which survives rehydration, drafting and grid edits; it's deliberately the **full** suffix `"Broadcast Schedule (:15/:30 Broadcast Video)"` rather than `"Broadcast Schedule"`, because the shorter string is the `broadcast_tv` product's own label and matching it would exempt a hand-entered rate-card line too. Renaming the tactic forfeits the exemption, which is what the caption warns about. When a draft is involved the rule also goes into `unresolved`, since a reviewer flipping the agency toggle and seeing one line's total not move deserves an explanation.

  **An imported schedule replaces the rate-card broadcast line rather than joining it** — they describe the same buy, and both would double-count the spots. Station → market is a lookup, never a guess: `WUSA`→DC, `WPMT`/`FOX43`→Harrisburg, and anything else is reported so the seller sets the geo by hand (a wrong DMA on a media plan is the sort of error a client catches). Impressions and cost come from the WO summary and the **CPM is derived** from them rather than read off the export, whose CPM is rounded to cents — rounding it back out would leave the plan a few dollars off the schedule slide. Under a monthly breakout both are divided by the month count, so the plan reads per month while the schedule slide reads the whole flight; `tests/test_broadcast_e2e.py` asserts monthly × months ties back to Wide Orbit's own totals, which is the agreement a client would check and the failure nobody would otherwise notice.

### The broadcast row's Flight is schedule-derived, and the coverage warning compares against active months only

- **FLOW_REWORK_PLAN.md Phase 2 closed a real gap: an imported schedule's Flight cell used to read the plan's own flight text, not the schedule's.** Geo and Targeting were already held verbatim on a shared-field re-seed (see the broadcast-exemption entry above) — Flight wasn't, because `resolve_row_defaults`'s `current is not None and is_broadcast_row(...)` block held `Targeting`/`Geo` but returned `flight_label` unconditionally, and `broadcast_row_for` seeded the row's Flight from the plan's own `flight_label` in the first place rather than `ScheduleSummary.flight_start`/`flight_end`. Both are fixed the same way Geo already was: `broadcast_row_for` now renders the schedule's own dates through `format_flight_shorthand`/`flight_month_ranges` (falling back to the plan's flight text only when the export gave no parseable week dates at all), and `resolve_row_defaults` holds `current.get("Flight")` the same way it holds Geo and Targeting. Guard: `tests/test_broadcast_e2e.py`'s Flight assertions, added alongside its existing Targeting/Geo ones, which make the same edit (editing the shared Audience field, which re-seeds every clean row) and confirm Flight survives untouched and differs from the plan's own flight text.
- **The Wide Orbit coverage warning compares the schedule's own months against the plan's ACTIVE months, not every month the flight spans — decided explicitly, not left to Phase 2's own ambiguous wording.** Before per-month ranges existed there was no difference between the two; once a rep can skip a month, a schedule running inside a skipped one is exactly the mismatch this warning exists to catch, not noise to suppress. Comparing against every calendar month the flight spans (including a skipped one) would bury that real warning among reports about months nobody's buying — and noise in a warning is how real warnings get ignored.

### Wide Orbit schedules: one shape, and the units are the trap

- **Wide Orbit schedules parse into one shape, and the units are the trap.** `wideorbit.parse_schedule` reads all three export formats — Campaign Schedule Report `.xlsx`, Planner `.xls` (needs `xlrd`), Planner `.pdf` — into `Schedule(rows, summary)`. Impressions arrive **in thousands in the Planner exports and raw in the Campaign Schedule Report**, so `normalize_impressions` decides by reconciling against `cost / cpm * 1000` rather than trusting a per-format rule; the format's own convention is only the fallback when there's nothing to check against. Guessing wrong is a 1000x error in a client-facing plan. Two things the real files taught: the `.xls` puts **per-spot** audience in the labelled `(000)` column and the row's extended total in the *unlabelled* column beside it (summing the labelled one under-reports by the spot count), and the `.xlsx` week columns are M/D with no year on a schedule that crosses New Year, so the year advances when the month goes backwards. The demo label varies per schedule (`A25-64`, `CS-A25+`, `A35+`) and is carried through, never hardcoded. `$0.00` added-value rows are real inventory and are kept. Parse failures raise `ScheduleParseError` with a message aimed at a seller, so the caller falls back to manual entry rather than showing a stack trace. **The test fixtures are real client schedules — real advertisers, rates and an AE's contact details — and are gitignored, like the decks.** `tests/test_wideorbit.py` expects `ravens_campaign_schedule.xlsx`, `regency_planner.xls` and `regency_planner.pdf` in `tests/fixtures/wideorbit/` and reports SKIP without them, so the suite still runs for anyone who doesn't have them.

### The schedule's summary block is anchored to the table

- **The schedule's summary block is anchored to the table, not to the template.** It carries the flight's own impressions/spots/gross/reach/frequency and sits at a fixed height in the master, with the table sized to fit above it — which holds only for as long as the summary is what `_content_floor` finds beneath the table. The moment the floor resolves to something lower (an empty footer shape at 6.94in, say), the table grows straight through it and a page of programs renders on top of the flight totals. `place_summary_below_table` runs *after* `condense_media_plan_table` and puts it at the table's real bottom plus the same 0.25in clearance, clamped so it can never be pushed off the slide — a table that has genuinely overrun already warns, and hiding the evidence isn't a fix. The shape has to be captured **before** `fill_bullet_list_in_slide`, which consumes the `{{BROADCAST_SUMMARY}}` token it's found by. Continuation pages drop the summary entirely (that's also what raises their floor), so only the final page has one. `tests/test_wideorbit.py` asserts the gap on every page that has one, because a schedule overprinting its own totals is invisible to every check that only measures the table.

## Layout, fitting and text measurement

### Slide content is fitted to the slide

- **Slide content is fitted to the slide, not assumed to fit.** Two overflow bugs came out of live testing and both fixes are load-bearing. (1) The **media plan table's floor is derived from the slide** — the topmost shape below the table that overlaps it horizontally — not looked up by shape name; the old code anchored to `"Picture 12"` at 4.70in and missed that the "Included with Campaign:" heading starts higher at 4.63in. (2) **Row heights alone don't bound a table**: PowerPoint grows a row whose text doesn't fit, so font size is derived *from* the final row height (and cell insets zeroed) rather than picked off a coarse ladder. At high row counts the header and totals rows shrink to the same floor as the data rows — clamping them at half their template height left 12 rows plus a full-flight row overflowing by 0.21in. Past the point where every row is at the minimum readable height the table genuinely can't fit, and that reports a warning naming the line limit instead of shipping an overlap. (3) **Campaign Specs** is one tall frame with no autofit in the template, so drafted copy ran over the client-name block; it's now measured and scaled in steps to a 60% floor, then warns to shorten. python-pptx can't measure rendered text and PowerPoint's `normAutofit` only recalculates on *edit* — a generated deck that's merely opened keeps the stored scale — so sizes are estimated here and written onto the runs, erring high (guessing high costs whitespace, guessing low costs an overlap). `personalize()` returns these warnings; the caller surfaces them. **When testing this, locate the plan slide by its table** — two slides contain "Included with Campaign" and measuring the wrong one reported PASS everywhere while the real 12-row case was broken. (4) **The Campaign Specs client name is a width problem, not a height one**, and it is the one place a *shrink* is decided from a horizontal measurement. Its box is `wrap="none"` with `<a:spAutoFit/>`, so PowerPoint neither wraps a long name nor (on a file that is opened rather than edited) resizes the box around it: the name draws straight out of the dark panel and across the slide. Ordinary, not an edge case — "Ridgeline Heating & Air" measures 407pt against 321pt of usable box at the template's 42pt. ``fit_no_wrap_title` runs in two phases. **Phase 1 shrinks on one line and is byte-identical to the single-line version** — anything that fits is sized exactly as before with its box untouched, which the tests assert on the shape geometry, not just the font size. **Phase 2 is reached only by a name that would otherwise have been held at the floor and reported as overflowing**: wrapping is switched on and the ladder walked again against a two-line budget. That case was not hypothetical — *Blue Ridge Bank & Trust Company Incorporated* is a real client, and at the 16.8pt floor it drew 405pt into a 359pt box with nothing but a warning; wrapped, it sits at 25.2pt. **The wrapped block grows upward from a fixed bottom**, because the gap to the "Campaign Specs" heading below is only 46pt — nowhere near a second line — while there is 5.13in of empty panel above the title with nothing in it. `_reflow_wrapped_title` anchors the last line to where the *template's own* 42pt line ends, not to where this (smaller) one would, so a wrapped title sits exactly where an unwrapped one does; for one line at the template size the arithmetic is the identity, which is what keeps phase 1 untouched. A name needing a third line takes the floor **and** warns, but is still reflowed for the lines it actually takes — growing into empty panel beats overprinting the heading, and the warning still fires, so nothing is hidden. It takes 92 characters to reach that. **Wrapping is counted by deflating the available width, not by inflating the measurement** (`usable / correction`), so text_metrics' own greedy wrap — the algorithm a renderer uses — is reused rather than reimplemented; and a line count of 2 is not on its own proof of fitting, since greedy wrap lets a single over-wide *word* overflow, so `_longest_word_pt` is checked too. **COM verification is against the template's own rendered line, not against the heading below it**: the title's bounding box legitimately overlaps that heading's box by ~4pt of font leading even in the untouched template, so "does it overlap Campaign Specs" reports a failure on a slide that is correct. The invariant that means something is *no title sits lower than the template's own line does* — verified at 423.2pt for one, two and three lines alike.

### Silent font substitution and the measured width-ratio table

- **A third silent font substitution, and this one can't be fixed by finding the font.** The two earlier Calibri incidents were both wrong *lookups* (no index entry for Proxima Nova; the wrong slide master's theme). This one isn't: the Campaign Specs title asks for **Aptos Black**, which is on none of these machines — PowerPoint renders it from the deck's **own embedded font data**, which is EOT/`TTCOMPRESSED` and which PIL cannot open (see the embedded-fonts note above; don't re-litigate extracting them). So the renderer draws the real face while `text_metrics` measures a Calibri Bold substitute ~16% narrower — the first version of this fit reported the name fitted and PowerPoint drew it through the edge of the panel anyway.

  **The correction is a per-face measured table, not one constant extrapolated everywhere** — `assembly._SUBSTITUTE_WIDTH_RATIOS`, consulted by `_text_width_pt` whenever `resolve_font` reports anything other than `exact`. Each entry is `max(real ÷ substituted width)` over six client-name strings (including a deliberately adversarial all-caps one, the glyph mix that produces the worst ratios) plus a 3% cushion for sampling error. Per-face spread over those strings was 0.026–0.119, so a face's ratio is a property of the face rather than an artifact of the string — which is what makes the table worth having. The installed faces were measured through `text_metrics`; **Aptos Black had to be measured through PowerPoint's `TextRange.BoundWidth` inside the master**, since it renders only from the embedded data. Ratios transfer between machines (they describe the face, not the box), which is why measuring them here holds on an instance where the face is missing — the only time they're consulted.

  **An unmeasured face gets the worst ratio observed on any face (1.41), not the value that happens to fit this deck's title.** Over-reserving shrinks a title slightly; under-reserving draws a client's name through the panel edge, and the direction to err is already settled. `_UNCALIBRATED_SUBSTITUTE_RATIO` is derived as `max()` of the table rather than typed in, and Tier 1 asserts the bound really does bound it — a face added above it would silently stop the default from defaulting to anything.

  **Three paths need three different corrections, and conflating them costs real type.** (1) Measured in the face itself → trust it. (2) Measured in *Calibri* because the face is missing → the table above. (3) **No font files at all** (the deployed instance) → a different mechanism entirely, since the character-ratio estimate isn't a measurement of any font; `real ÷ estimate` ranges **0.816–1.525** across the same faces and strings because the estimate ignores glyph mix, so it has its own table and its own looser bound (1.58). And separately: a run whose family is present but whose **bold cut** is missing is measured in that family's own regular weight, not in Calibri, and that fallback was already measured to draw *wider* than the bold does — so it gets 1.0 and is not reported. Inflating it would shrink type for room nothing needs; reporting it would cry wolf on every deck.

  **The extrapolation is surfaced where a person sees it.** `assembly.width_calibration_note()` names any face reserved for without a measurement of its own and says so, shown as an `st.caption` beside `text_metrics.measurement_note()` at generate time — two different facts (a substitution *happened* vs. the correction for it *wasn't measured against that face*), so two notes. The log is cleared per build, or a note about a font some earlier proposal used describes nothing. A log line nobody opens is the phantom-slide-37 problem in a different costume.

  **Self-calibrating from the deck was tried and doesn't work**: the title box is `spAutoFit` + `wrap="none"`, so PowerPoint sized it to fit `{{CLIENT_NAME}}` at 42pt in the real face, which looks like a free per-machine measurement of a known string. It yields 1.039 where 1.163 is needed, because braces and capitals aren't representative of a client name and the box is no longer tight. A genuinely per-substitution value at build time would need COM, which the deployed instance doesn't have.

  `check_client_name_fit` asserts twice — what the sizer decided, and, over COM, what actually got drawn. Only the second one caught the original bug. `check_width_calibration` covers the table policy offline and machine-independently.

### A cramped plan buys its type back from the Included band

- **A cramped plan buys its type back from the slide, not from the reader — and the band it buys from is legally load-bearing.** There are two font floors and conflating them is what left long plans at 6pt: `_MIN_TABLE_FONT_PT` (6) is the absolute floor, below which `condense_media_plan_table` warns; `_COMFORTABLE_TABLE_FONT_PT` (9) is the size below which a plan stops being readable across a conference table. Falling below the second isn't a failure, it's the signal to spend layout elsewhere. The threshold is expressed as a **font size, never a row count**, because the row count that reaches it moves with the content — changing only the Flight column from `Sep 1 - Nov 30` to `9/1 - 11/30` moved a six-row plan from 8pt to 12pt. On the real deck the ladder runs 12 → 10 → 8 → 7 → 6, so 9pt itself never occurs and the rule reads as "must not go below 10".

  **What it spends is the "Included with Campaign" band**, ~1.84in of a 7.5in slide against the table's 2.90in, almost all of it artwork — two decorative pictures around a list the app already renders elsewhere as one comma-separated line. `compress_included_band` drops the pictures and sets the list inline. But the plan slide is a **signable document**: it carries `Approved: ___ Date: ___` and the Premion terms, and that signature is only meaningful on a page that also states the totals, what's included and the terms. So the band may be made smaller and may be moved, and may **never leave the page the signature is on**. There is no version of this that lifts the band off "the long ones" — every plan slide is signable, since a multi-option deck gives the client one signature line per option and they sign the option they pick.

  **Three things about the order, each of which was a bug first.** (1) Deleting the pictures raises no floor on its own: `_content_floor` reads the topmost shape below the table, and the heading is still sitting at 4.63in. The band is therefore **parked** at its lowest legal position (just above the signature) during compression, sized against, then floated back up to the table's real bottom afterwards — the same order `place_summary_below_table` runs in. (2) Sizing runs **twice**, and `condense_media_plan_table` reads the template's row heights to decide the starting font — so a second call would take its own first-pass output for the template and lock in the smaller font. The `template_metrics` dict carries the template's heights across both passes. (3) `_tighten_cell_paragraphs` only ever *shrank* a run, which reads the run's current size and so compares pass 2 against pass 1's output: a plan given more room stayed at 8pt while the search had already worked out it could have 13. It now applies the size with `force=True`, safe because the search is capped at the template's **own** run size (12pt, recorded before the first pass overwrites it) rather than at the ~47pt `_max_font_for_row` derives from row height, which was never a ceiling at all.

  **The decision is per deck, not per slide** — sizing every option first, then compressing all or none — or a three-option deck ships one plan page with the decorative graphics and the next without. Measured effect with the band compressed: 9 rows 8pt → 12pt, 10 rows 7pt → 11pt, a 4-attribute stack at 6 rows 8pt → 11pt. Plans already at or above the floor are untouched and render byte-for-byte as before. `tests/test_draft_regression.py` spies on `_prepare_media_plan_slide` rather than the sizing step, because sizing now runs twice per slide and counting there reports every option twice.

### Text is measured, not estimated

- **Text is measured, not estimated, and the font it's measured in has to be the font it's drawn in.** `text_metrics.py` wraps strings against the real glyph advances (PIL `ImageFont.getlength`) instead of an average character-width ratio, and `assembly._wrapped_lines` / `_lines_in_row` go through it. Five things here are load-bearing and each was a real defect:
  1. **Fonts are discovered, not listed.** A hardcoded name→filename map had no entry for **Proxima Nova** — the brand font the master deck actually uses — so every measurement silently substituted Calibri, which is narrower, and under-measured every table. `_font_index()` reads the family/style out of every font file on the machine. A list you have to remember to extend fails silently the first time a deck uses a font nobody added, and under-measurement is the direction that overlaps. Bold is resolved to the bold face for the same reason.
  2. **Measure at a large reference size and scale down.** PIL takes an integer pixel size and quantizes glyph advances to whole pixels, so measuring 6pt text at 6px rounds every character and rounds *down* in aggregate: a Geo cell measured 115pt against the 119.5pt it had, "fit" on that arithmetic, and PowerPoint wrapped it. Measured at 512 and scaled, the same string is 119.62pt against 119.5 — it overflows by a tenth of a point, which is exactly what the renderer did.
  3. **The horizontal inset is not the vertical one.** `_DEFAULT_CELL_INSET` is the 0.05in top/bottom default; left/right defaults to 0.1in *per side*. Using the vertical constant for width over-stated every column by ~11pt. `_side_insets(cell)` reads the cell's own margins.
  4. **Rows are sized individually.** A row is as tall as its own tallest cell, so one height for every data row gives a row that wraps to two lines the same share as one that doesn't — and PowerPoint grows it past what was reserved. `condense_media_plan_table` now measures each row, reserves per row, and hands the leftover out evenly (grow-to-fill). Header rows are measured too — trusting the template's height left a "Wk / Total / Adults 25-64 (000)" header declared at one line and drawn at two. Rows added *after* sizing need their space reserved in advance: the full-flight totals row is cloned from the monthly one and says something longer, so `extra_total_label` is passed in and measured.
  5. **A slide resolves its fonts against its OWN master, and this deck has 21 of them.** Fixing the font *index* (1) only helps if something asks it for the right name. `register_theme_for_table` read `prs.slide_masters[0]`, and master 0 is the **only** one of the 21 whose minor font is Calibri — every content slide uses a Proxima Nova master. So `+mn-lt` resolved to Calibri and the entire project measured brand text in a narrower font it never draws, which is the same silent under-measurement (1) was written to kill, arriving by a different route. The theme is now reached through the slide's own layout → master (`_theme_part_for_slide`); `prs.slide_masters[0]` survives only as the no-slide fallback, which is correct just for a single-master deck. Symptom to recognise: a table that measures "fits" and renders one line taller, worst on the Total TV plan slide where the columns are narrowest. Caught by `validate_text_metrics.py` as a grown row, invisible to every assertion. Related: `_THEME_CACHE` is keyed on `id(table)` and now retains the table's XML element and confirms identity on read — an un-evicted id()-keyed cache is the ImportCache bug waiting to happen again.
  6. **Nothing substitutes silently any more, and the font list comes from the deck.** Two Calibri incidents (1 and 5) were both silent defaults, so `text_metrics` now records every resolution as `exact` / `substituted` / `unavailable` with a reason, logs the imperfect ones once, and exposes `resolution_report()` / `measurement_note()`. A *weight* fallback counts as a substitution — the master asks for **Proxima Nova Light bold**, which no machine here has, so bold cells measure in the regular weight. **The direction was then measured rather than assumed, and it is the opposite of the obvious guess:** asked via PowerPoint's own `TextRange.BoundWidth` at 12pt, `Proxima Nova Light` + bold *draws ~2% NARROWER* than regular Light (`TACTIC` 43.2→42.2pt, `Full Flight Total (3 months)` 138.1→134.8pt), so the regular-weight fallback **over**-measures — the safe direction. Do not "correct" it by promoting bold to a heavier face: Proxima Nova Bold measures 45.1/148.9pt on those strings, far wider than what renders, and over-reserving shrinks type for room nothing needs. A family name that ALREADY denotes bold or heavier (`Proxima Nova Extrabold`, `... Black`) resolves to itself as **exact**, not a substitution — asking for bold on top of it is a no-op, and reporting it put a false line in the log on every deck, which is precisely the cry-wolf failure this reporting exists to prevent. Matched on whole words: `semibold` contains `bold`, and a substring test would wrongly silence it (same trap as `"auto"` matching `"automatic"` in the vertical hints) — Semibold is lighter than bold, so it stays reported. `tests/test_font_resolution.py` pins the contract (31 checks, offline, machine-independent — the font index is faked, since a test that only passes where Proxima Nova is installed tests the box). `assembly.declared_fonts(prs)` reads the deck's own `<p:embeddedFontLst>` so the check follows the brand font instead of naming it; the master declares 14 faces and a typical Windows box has 7 of them (the Aptos and Nunito Sans families come in with imported case study masters). **The embedded font data is NOT usable for measurement, and this was checked properly rather than assumed**: all 36 `ppt/fonts/*.fntdata` parts are EOT 2.2 with the `TTCOMPRESSED` flag (MicroType Express, magic `0x504C`), which PIL cannot open and which has no practical Python decompressor — don't spend time on "just extract the embedded fonts" again. The note is shown as an `st.caption` and deliberately **not** appended to `personalize`'s warnings: it is true of every deck a given machine builds, and a permanent entry in the channel that means "this deck has a layout problem" is how a warning stops being read.

  **Local and deployed do not measure identically, and the gap is measured rather than guessed.** Streamlit Cloud has neither the brand fonts nor Calibri, so it falls all the way through to `FALLBACK_CHAR_WIDTH_RATIO`. Running the boundary row counts through the real `personalize` twice — once with the font index emptied — the two environments pick the **same** font in 9 of 10 cases and make the **same** band-compression decision in 10 of 10; the one divergence is a 10-row stacked plan at 8pt locally and 7pt on the estimate. The estimate errs wide, which is the safe direction (it reserves too much and shrinks sooner). Bundling the font files would close the gap and is a licensing question, not a technical one.

  **Two decisions, settled — don't reopen them without new evidence.** (1) **Font bundling: declined.** The measurement above is the reason: same font size in 9 of 10 cases, the same band-compression decision in 10 of 10, and the one divergence errs toward *shrinking* rather than overlapping. That is not worth a commercial-font licensing review. (2) **`min_table_row_height()` at 0.2in against PowerPoint's ~0.3in floor: won't fix.** PowerPoint will not draw one of these table rows shorter than about 0.3in whatever height is declared, so a row declared at the 6pt minimum (0.2in) is drawn taller and `validate_text_metrics` reports it as grown — currently three rows, one added full-flight totals row and two 6pt schedule subtotals. It is a model imprecision with **no visible symptom**: all three sit inside their real floors (the ashford plan clears the Included band by 0.18in; the validator flags it only because it measures against floor-minus-clearance). Raising the constant would cost real capacity on every table to fix nothing anyone can see, and tuning it to a number that only looks right on paper is what the `_ROW_CUSHION` note already warns against. Left alone deliberately; revisit only if a real deck shows an overlap.

### Reserving vs refusing; validating against the renderer

- **Reserving generously and refusing generously are different things.** `_row_height_for` keeps a 0.1in per-row cushion because PowerPoint draws these table rows taller than their content accounts for — a 9pt single-line schedule row comes back 0.3in tall however little is in it, where the same row in a table built from scratch honours 0.15in; nothing in the cell XML explains the difference, so the allowance stays rather than being tuned to a number that only looks right on paper. But the "this table cannot fit" warning is judged on `_row_text_height` (the bare lines, no cushion), because twelve rows of cushion is an inch of space nothing really requires — judging the warning on reserved height declared a 12-line plan too tall for a slide PowerPoint then drew it on with a quarter inch to spare.
- **Validate layout against the renderer, and read PowerPoint's row heights correctly.** `tests/validate_text_metrics.py` opens each rendered scenario over COM and compares. The subtlety that makes or breaks it: PowerPoint reports a row's height as **max(declared, what the content needs)**. A row reported at its declared height therefore says nothing about how many lines were drawn — the sizer grows rows to fill the slide, so a one-line totals row can sit in half an inch, and deriving a line count from that measures the sizer's own output rather than the renderer's. A first version did exactly that and reported 84 disagreements that were entirely artifacts. The real signal is a row reported **taller** than declared: the text didn't fit and PowerPoint grew it, which is what pushes a table over the block beneath it. Two more traps: pair tables by a **signature** (slide, shape, first row), never by index — COM enumerates only top-level shapes while python-pptx recurses into groups, so the orderings drift apart on any slide with a grouped table; and scope the check to the tables the sizer actually manages (`_find_table_shape` on a slide whose text says MEDIA PLAN), or imported case study tables — somebody else's layout, with their own fonts and merged cells — get held against this code's arithmetic.

## Drafting, the catalog and the Claude API

### Vertical detection

- **Vertical detection matches whole words over one combined table, longest phrase first.** Discovery notes name a business the way its owner would ("an HVAC company", "a credit union"), never by vertical key, so `VERTICAL_HINT_SYNONYMS` carries ~136 trade names across all ten verticals. Two things that look like details and aren't: (1) matching is **word-boundary regex, not substring** — naive `in` fires "tire" on "the entire campaign", "venue" on "revenue", "spa" on "Spanish", and (a live bug this fixed) "auto" on "automatic"; (2) trade names and the verticals' own names/labels are matched in **one table, longest phrase wins**, rather than names-first-then-trades — a two-pass version resolved "credit union promoting auto loans" to `auto` on the incidental mention. `"auto"` is in `AMBIGUOUS_VERTICAL_TERMS` and never matched on its own (the label "Automotive" is unambiguous and does the job). Vertical names/labels are folded in automatically, so a newly added vertical is matchable before anyone writes synonyms for it. Terms describing *what's being advertised* rather than *who's advertising* don't belong here — "concert" was dropped for "concert venue" because a casino promoting a concert series is still a casino. `test_vertical_hints.py` covers every vertical plus the false-positive guards; run it directly, no framework. **Apartments, realtors and property management are deliberately unmapped** — none of the ten verticals fits them (home improvement is contractors, not property sales) and a wrong hint costs the model the right slice of the catalog. They need a Real Estate vertical.

### $0 rows, and Dynamic Video Ads

- **A $0 media plan row is always wrong, and the draft is where they came from.** A "Commercial Production (:30 spot) — $0" row appeared in a real deck; nothing in the seeding code creates it. Production is normally included at no charge and the model expressed that as a zero-dollar `custom_fee` line instead of an Included-with-Campaign entry. Fixed at both ends: the prompt says outright that no-charge items are not plan lines and names `commercial_production` in `attribution` as where they go, and `resolve_drafted_lines` drops any line resolving to $0 whatever its source, with a note. Note the distinction — a freshly *seeded* rate row is $0 by design (the seller types impressions or cost into it); it's **fee** rows that must never be zero.
- **Dynamic Video Ads are a flat fee, and were an orphaned key until now.** The slide always carried `dynamic_creative` but nothing switched it on, so it could never ship (one of the two orphans flagged in SLIDE_KEYS.md — `case_study:retail` is still the other). Its Section C toggle both includes the slide and seeds a `Dynamic Ad Creation` **flat-fee** row, because it's a one-time creative build rather than impressions. It sits in `PRODUCT_TO_WIDGET_KEYS` so `DRAFT_KEY_SECTIONS` tags it `products` (matching its widget's `on_change` section) *and* in `ATTRIBUTION_FIELD_MAP` so a draft can enable it — but it's excluded from the media-plan line namespace via `NON_LINE_PRODUCT_KEYS`, or a drafted line could name it, find no CPM and produce exactly the $0 row above.

### Audience catalog is scanned from the brochure PDF

- **Audience catalog is scanned from the brochure PDF, never hand-transcribed.** `audience_catalog.py`'s `load_audience_catalog()` (cached with `@st.cache_data`) parses `PREMION_Audience Targeting (1).pdf` — segment name, category, subcategory, and Salesforce RFP-selectable status (detected via the light-cyan highlight rectangle behind each RFP-selectable line, a fill shape, not a text-color property) — then merges in `times_used` from `audience_segments_derived.csv` (that CSV's own `category`/`is_custom` columns are not used; the PDF is the authority on those). If the brochure is ever replaced, re-verify against page 2's own condensed "accessible in Salesforce RFP" roster the same way this was validated (104/105 exact agreement on first build; the one mismatch was a genuine "Parent"/"Parents" typo already in the source PDF) — don't assume a new PDF's layout quirks match. Two non-obvious PDF-geometry gotchas if the parser ever needs revisiting: (1) a subcategory's segment list snakes across the page's column bands without repeating its header in later columns, so the running "current subcategory" must be tracked *per category code*, not per column or as one single value — different categories' sections interleave in raw column-then-top reading order; (2) some categories spell their subcategory headers out in full ("FINANCE", "HEALTH", "ENTERTAINMENT") while segment rows use the abbreviated code ("FIN", "HLTH", "ENT") — `HEADER_CATEGORY_ALIASES` bridges the two.

### Prompt rules stated positively; avails ingestion and basis

- **The drafting prompt states rules positively — a rule that quotes what it forbids can teach the exact output it is trying to prevent.** The review-list rules said *"Never use an internal identifier. Not `rfp_selectable: false`, `custom_fee`, `audience_track`…"* — and a live run produced an internal item reading *"…is rfp_selectable: false — confirm it is available to book"*, using the very string the rule quoted to ban. The banned token is the most salient phrasing in context, and quoting it makes it available to copy: the prohibition supplied the vocabulary. All three prohibitions of that shape were rewritten as positive instructions carrying the preferred wording instead — the identifier rule now names what a seller *would* say ("a custom audience", "not directly selectable in Salesforce", "the production fee line"), the plain-sentence rule keeps its good example and drops the bad one it used to quote in full, and the rate rule says to write a plain JSON number rather than quoting the `$28` / `28 CPM` forms it rejects. **`rfp_selectable` itself cannot be removed from context** — every entry in the catalog slice carries the flag and the one-custom limit depends on the model reading it — so the fix there is to put the plain-language substitute *at the point where the flag is explained*, which is where the model would otherwise reach for the field name. Generalise it: in this prompt, say what to write, not what not to write; a negative example is a sample of the thing you don't want, sitting in context, ready to be echoed.
- **Avails are ingested when the notes supply them, invented never, and always stored monthly.** The old prompt rule said *"never invent a Max Monthly Avails number — that field doesn't exist in this schema on purpose"*, which implemented "never fabricate avails nobody supplied" as "never accept avails at all": a rep who had already pulled the numbers and put them in the notes still got a table of zeroes and a chore. `audiences[]` now carries **`max_avails`** and **`avails_basis`**, populated only from a figure the notes actually state — never estimated, never carried across from another audience, never worked back from a budget or a CPM, because a fabricated avails number is indistinguishable from a real one to whoever sends the proposal. Absent stays blank and is flagged for the seller (`unresolved_internal`), exactly as before. An audience whose name **doesn't** resolve to a catalog segment but which came with a real number keeps the rep's label as typed alongside the figure and is flagged — dropping the row would throw away the one thing that had to be looked up by hand.

  **`percent_of_avails` is the fifth allocation type, and the only one whose impressions are the input.** `{"percent_of_avails": 20, "avails_ref": "<segment>"}` — the model states a percentage and which audience it refers to, and Python does all of it: impressions = avails × percent, cost = impressions ÷ 1000 × CPM, markup as normal. It resolves in a **stage 0** ahead of the budget waterfall so its cost is known before the remainder is worked out, like a flat amount. Three failure modes are named rather than guessed at: blank avails leave the line on the plan with blank impressions and cost (it is deliberately **exempt from the $0-line drop** — dropping it would discard the audience and share the notes did specify, and filling the avails in makes it price itself), a percentage over 100 is flagged, and a reach figure that disagrees with a stated budget is resolved **from the reach** with the discrepancy flagged. These rows also drive from **impressions** rather than cost — the one place `resolve_drafted_lines` returns a per-row driver, since for every other line the dollar allocation is the specification and impressions are derived.

  **The basis is a display question; storage is monthly, full stop.** The avails system reports monthly, so monthly is the one basis that never needed converting to get here, and a reach percentage, a rebuild and a rehydration all read the same figure. The D2 toggle changes what is *shown* — and the column header with it (`Max Monthly Avails` / `Max Avails — Full Flight (N months)`), including on the slide, where that header is **literal text rather than a token** and is rewritten by `assembly.set_avails_column_label` run-by-run. **A row the user didn't touch is never round-tripped**: converting monthly → ×N → ÷N is exact only while N divides cleanly, so flipping twice on an odd figure would walk the stored number a unit at a time and the drift would land in something a client is quoted. `restore_untouched_avails` keeps an unedited row byte-for-byte and converts only what actually changed — asserted through the real widget in `tests/test_avails_reach.py` by flipping 333,333 over a three-month flight four times. **Reach is invariant to the basis** (20% of monthly avails across N months is 20% of the flight total), which is the property that makes the toggle safe to offer at all, and it has its own assertion. History stores `avails_basis` and the resolved `avails_label` (stored, not recomputed, so a rebuild can't disagree with the month count it was built from) plus a per-row `avails_monthly`; rows logged before any of this existed carry none of it and were monthly, which is exactly what the fallbacks give them.

### A failed Claude call has to say which failure it was

- **A failed Claude call has to say which failure it was, and the response ceiling is sized against the biggest realistic draft.** A large live scenario (three audiences with avails, two options, ~six lines each) failed with *"Claude's response wasn't valid JSON even after stripping markdown fences: Expecting value: line 1 column 1 (char 0)"*. **Char 0 means the text was empty** — the fence-stripping the message blamed was never involved, so the message sent the reader somewhere the bug wasn't, and nothing was logged, so a run that cost a live API call and a long wait produced no evidence. Three things came out of it. (1) **`ANTHROPIC_MAX_TOKENS` was 2000, below what a real draft needs**: the largest realistic draft — two options of six lines, three audiences carrying avails, full Campaign Specs, both review lists at their 8-item cap — measures ~12,400 characters of pretty-printed JSON, about 3,500 output tokens. It is now **16000**, which is also the practical ceiling for a **non-streaming** call; raising it further means moving to `client.messages.stream()` + `get_final_message()`, not just editing the number (Sonnet 4.6 itself allows 128K output). `tests/test_claude_call.py` pins both halves by rebuilding that draft and measuring it, so the constant can't drift below the thing it exists to cover. (2) **`stop_reason` is read before the JSON is parsed** — truncated JSON fails to parse, so a `max_tokens` cut-off was being reported as a formatting problem; `refusal` and an empty body are named as themselves too, and `stop_details` is only read on a refusal (it is `None` otherwise). Text is joined from **every** text block rather than `content[0].text`, since a pre-output refusal returns no blocks at all and the old code turned that into a bare "Claude API call failed". (3) **Every call is logged** — label, stop reason, input/output tokens, the ceiling in force, request id, and the first and last 200 characters — to the console (visible in Streamlit Cloud's log viewer) and to `%TEMP%/proposal_builder_claude_calls.log` (survives locally). Logging failures are swallowed: the draft is the point, the log is the evidence. Empty/truncated/unparseable responses retry once before anything reaches the seller; a refusal does not, because it would only refuse again.

  **The char-0 failure came back on a genuinely open-ended notes set (LiveWell Animal Hospital, RFPID-266894 — no stated budget, two multi-location scenarios), and this time the ceiling wasn't the cause.** Reproduced live: 18,026 input tokens (well under prompts that already succeed at 70K+), `stop_reason: "end_turn"` on both attempts — nothing truncated. The model opened both attempts with a reasoning preamble ("I need to analyze these notes carefully before building the JSON...") despite the prompt's explicit "no preamble" instruction, and since the retry resent an identical prompt, it failed identically twice. The historical log already had two other real scenarios with the same shape (an SR&B agency net-rate case, a reach-based multi-option case) — this was latent, not new, and just needed a judgment-heavy notes set to surface it.

  **An assistant-turn prefill (`{"role": "assistant", "content": "{"}`, the standard technique for forcing a response to continue directly from seeded text) was tried as the structural fix and doesn't work on this model.** `claude-sonnet-4-6` rejects it outright: `400 invalid_request_error` — *"This model does not support assistant message prefill. The conversation must end with a user message."* Confirmed live before the fallback was even written, then fully reverted — no flag, no dead branch left in place. **Don't re-attempt prefill on this call without re-checking that constraint against whatever model is current at the time** — it may change with a model version and hasn't been re-verified since.

  **The first version of the fix — `_extract_first_json_object`, taking the FIRST balanced `{...}` in the response — shipped, and it silently corrupted a real LiveWell draft the same day, caught only by reading the output rather than checking that it parsed.** A preamble routinely quotes a small schema fragment verbatim while the model reasons about a choice ("I'll use group_selection: `{"mode": "all"}`, since the notes describe the whole buy") — and that fragment is itself complete, valid JSON. Taking the first complete object found grabbed exactly that two-word fragment and returned it as the entire draft: no error, no crash, `outcome: "ok"` in the log, and every plan row silently zeroed out — objectively worse than the crash it replaced, which at least stopped loudly and let the rep retry. **The fix is `_extract_largest_json_object`: scan every top-level balanced object in the text and return the longest, not the first.** The real draft is overwhelmingly larger than any fragment quoted in passing, whether the noise around it is a preamble, trailing commentary, or both — verified against the exact failure shape (`tests/test_claude_call.py`'s `test_extract_prefers_the_real_draft_over_a_quoted_schema_fragment`, built directly from this incident) and live: re-run against the same LiveWell scenario, the model still opened with a preamble, and the full ~40,000-character draft came through intact both times. **The general lesson, not just this function's: "does it parse" is not "is it right" — a salvage/fallback path needs its own adversarial case (something small-but-valid sitting in front of the real answer), not just a case proving it recovers from garbage.** The retry was fixed independently, for the *other* failure shape: it now appends a corrective instruction to the prompt ("your previous response could not be used, return ONLY the JSON object...") rather than resending an identical one, so a genuinely different failure still gets a real second attempt instead of a guaranteed-identical repeat.

  **Every rep-facing message from this call path is plain language now, and the same grep swept six other call sites carrying the same shape.** The old empty-response message pointed a rep at `%TEMP%/proposal_builder_claude_calls.log` — a path that doesn't exist on Streamlit Cloud, where the rep who actually hit this was. The rule going forward: a user-facing error says what happened, then what to do (retry, then "Report an issue") — no file paths, session keys, or function/constant names; the real diagnostic detail (stop_reason, first 200 chars of the response) goes into `st.session_state["last_claude_failure"]` instead — scoped to the single most recent failure, cleared on the next success, never a full transcript — which `capture_feedback_state` folds into a rep's own "Report an issue" so a report is actually diagnosable without shell access to wherever the rep happens to be running. `grep 'st\.error(f?"[^"]*\{exc\}'` (plus its audience-usage-import cousin, `raise UsageImportError(f"...{exc}...")`) found the other six sites carrying a raw exception straight into a user-facing string: two `.pptx` open/read failures, a workbook read failure, `apply_draft_to_form` failing on both the draft and re-draft path, and the deck-assembly failure. Each still prints its exception to console — nothing lost for whoever has shell access — but shows only plain language on screen. Deliberately **not** touched: `db.py`'s `describe_error`-based fallback warnings, a distinct, pre-existing, already-documented convention for "Supabase is unreachable" messages — a separate architecture serving a separate purpose, not this incident's shape.

  **With the JSON-shaped bugs fixed, an actual end-to-end LiveWell run (7 real locations sharing one audience, no stated budget) surfaced two more things — one a prompt gap, one an app-side gap the prompt can't reach.** Judged as output, not just as valid JSON: entity grouping was correct (7 distinct locations, correctly left unmerged — `group_entities: null` — since they're genuinely different real-world things sharing an audience label, not one thing described seven ways), and it caught two real data-quality issues in the source avails PDF unprompted (a missing radius qualifier on one row, a "Mile Radius" missing its leading digit on another) plus a real discrepancy the notes themselves created (they say "eight locations," the avails table only has seven). But `total_budget` came back `0` on both options, every row priced at $0 — even though the notes explicitly say *"the plan should be built around an investment level that makes sense for the audience... rather than forcing the campaign into an arbitrary budget"*, i.e. an instruction to estimate, not silence to work around. The prompt had no case for "notes ask you to propose a number" distinct from "notes don't mention budget at all," so the model defaulted to the safe-for-the-wrong-case answer. Added a paragraph naming this case directly, with a concrete anchor (estimate against 10–20% of the audience's own avails at rate-card CPM) and the same "flag it as a seller estimate" treatment as any other assumption — and confirmed it's scoped correctly: re-run against notes that are genuinely silent about budget (no request to propose anything), `total_budget` stayed `0` with the original "cannot be priced, confirm with the client" wording, untouched by the new paragraph. Re-run against LiveWell's real "estimate it" notes: `$6,000`/`$28,000` came back, correctly split `$4,000` per location (28000 ÷ 7 distinct entities, exactly the entity system's own design), each flagged in `unresolved` for confirmation. One more misroute fixed the same pass: an internal vertical-categorization question landed in client-facing `unresolved` (a client is never asked which internal category to file them under) — the routing rule now names that case as an example.

  **The tripwire for revisiting "should this call be split into two":** today's evidence argues against it — two real failures, both closed by one-paragraph prompt edits, and the SAME pass that fixed the budget gap also got entity separation across 7 locations, correct per-entity allocation math, two real PDF-anomaly catches and a location-count discrepancy right simultaneously. That's capacity, not overload, and a split would roughly double both token cost and latency (most of the ~18K input tokens is reference data — the catalog slice, the avails/group table — that any split-off sub-task would still need in full) to fix a problem this run didn't show. **The actual signal to revisit it is a DIFFERENT failure shape: repeated LOOKUP misses (wrong or missing segments, geos, entities) rather than judgment misses (a missing instruction for an ambiguous case, a misrouted note).** A lookup miss says the model is losing track of the reference data itself under load — the argument FOR narrowing what one call has to hold at once. A judgment miss, like both of today's, says an instruction was incomplete or ambiguous — fixable by writing the instruction, not by giving the model less to do at once.

  **Found and root-caused, not yet fixed: every option's row list carries every globally-selected group, not just the ones that option's own drafted `group_selection` chose.** Traced precisely: `apply_draft_to_form` computes each option's INITIAL rows correctly, scoped to that option's own `matched_ids` (via `match_groups_to_selection`) — "Alexandria Only" starts with exactly one row. But it also flips `include_in_plan = True` on every group ANY option matched, globally, with no per-option memory of who wanted what — so by the time both options in one draft are processed, all 7 groups are globally included. On the very next rerun (before a rep even sees the plan), `reconcile_group_plan_lines`'s row-seeding step reads only that global flag, not the per-option intent, and adds a $0 row to "Alexandria Only" for the other 6 -- even though `draft_plan_intent` already stores each option's own resolved `matched_ids` (used elsewhere, for re-pricing, but never consulted for which rows belong on which option in the first place). Confirmed this reaches the deck, not just the grid: `compute_plan_totals` only skips a row with an empty Tactic, never a zero-cost one. Real per-option row scoping already exists as data (`draft_plan_intent[...]["selection"]["matched_ids"]`) — it just isn't read at the one place that decides which rows to seed.

### The AI draft path does no arithmetic

- **The AI draft path does no arithmetic — Claude returns intent, Python does the math.** `app.py`'s "Draft from notes" panel and "Audience finder" → Suggest mode both call Claude (`claude-sonnet-4-6`, JSON-only response contract, markdown-fence-stripped and retried once on an empty, truncated or unparseable response — the retry is real now; this note claimed it for a long time while no retry existed in the code). The draft prompt includes today's date and an explicit "resolve a year-less date to the next upcoming occurrence, never the past" rule (flagged in `unresolved` either way) — without it, the model would default a bare "September through November" to whatever year it last trained on, not the real current one. The two prompts also share one `AUDIENCE_MATCH_GUIDANCE` string telling the model to prefer a specific matching segment (e.g. a FIN segment for "in-market for deposit accounts") over a generic demographic proxy (e.g. a DEMO homeowner/income segment) — both send the model the *same* vertical-relevant catalog slice already (verified: all 22 FIN segments are present in a banking-vertical slice), so a mismatch between the two paths' picks was a prompt-emphasis gap, not a missing-data one.

  **A drafted plan is authoritative over Section C, and sports have their own product namespace.** Two bugs found in live testing shared a root: an NFL-only proposal came back with a Premion Streaming TV line the notes never asked for, priced at the Premion CPM. Sports aren't in `PRODUCTS` (their rates come from the per-sport ratecard, not one product default), so the model had *no way to express a sports line* and reached for `premion_streaming_tv`, inheriting its $32 CPM instead of the $66 NFL playoffs rate. A line can now name a package as `"sport:<sport_key>"`, resolved through `line_product_spec` — one shared lookup that both the form's own row seeding and the draft path go through, so they can't drift on rates again. The spurious product needed *both* halves of a fix: the prompt now states outright that there is no mandatory line and no default product (sports-only, AM-only, retargeting-only and single-line plans are all valid, and silence in the notes belongs in `unresolved`), **and** the draft clears every product toggle before switching on only the ones its lines use — Section C checks Premion Streaming TV by default and nothing ever unchecked it, so its slides came along regardless of what the model returned. Sports selection is the union of the `sports` array and any `sport:` lines, so a sports line can't be billed without its deck slides or vice versa.

  **One clarification round, with hand edits protected at section granularity.** After a draft, a "Clarify and re-draft" box takes plain-language answers to the `unresolved` questions and sends the model *its own previous JSON* back alongside the original notes, instructing it to revise rather than restart (change only what the answers bear on, keep everything else byte-identical, drop only what's now settled). Offered once — `draft_round` gates it, so the box doesn't reappear after the re-draft. Edits the user made between the two drafts survive because `DRAFT_KEY_SECTIONS` tags every session_state key the draft writes with the section its *widget* belongs to (the one its `on_change` clears): a section that was AI-filled in round one and has since been cleared is one the user hand-edited, and `apply_draft_to_form(draft, skip_sections=...)` drops those writes. Note the media plan's internal `_product_seed_key`/`_shared_fields_key` are tagged `media_plan` too — skipping the rows but writing the bookkeeping would leave the seed keys claiming rows that were never written. Preserved sections are named back to the user in the review list rather than silently kept.

  **A drafted budget is always a campaign total; the breakout is a separate, presentational question.** These are easy to conflate and the first attempt got it wrong. A budget in the notes ("a $40K plan", "$20K a month totalling $100K") is what the *whole flight* costs — `resolve_drafted_lines` therefore always works in full-flight amounts. How the plan is *presented* is independent: monthly is the normal case and is what per-month phrasing asks for. Under a Monthly breakout the rows hold per-month figures, so `spread_rows_over_months` divides the rate rows across the flight, which keeps the full-flight total on the number the notes quoted instead of multiplying it by the month count. That division is deliberately **not** rounded to whole dollars — rounding would make month × count miss the quoted budget (a $100K plan over three months would total $99,999), and it's the flight total that has to tie to what the client was told; the Cost column displays whole dollars anyway. Flat fees are one-time and are never divided. The schema's optional `breakout` field lets notes ask for a single combined flight period, defaulting to monthly and falling back to monthly on anything unrecognized.

  **The seed key is built by `read_seed_selections` and nowhere else — a hand-rolled copy silently wipes every drafted plan.** `apply_draft_to_form` has to precompute the `_product_seed_key` that `main()` will independently derive after the rerun; if the two disagree, main() takes its "product selections changed" branch and **rebuilds every option's rows from `_seed_option_rows()`**, which are freshly seeded $0 rows. Only the rows are replaced, so the option *names* survive — which is exactly what makes the failure so misleading. It presents as "the budget allocation is broken": correctly named options, correct products, correct CPMs, every impression and cost zero. The allocation waterfall is fine and was never involved. This happened because the draft handler assembled its own copy of the selections dict and `dynamic_creative` was later added to `read_products_selection` but not to the copy — and since the key is compared as `str()` of the whole structure, a *missing key* mismatches even when every shared value agrees, so it fired on **every** draft, single-option and multi alike. `read_products_selection(get=None)`/`read_seed_selections(get=None)` now take an optional getter (the draft path passes one that prefers its pending `updates`), so there is one construction and drift is structurally impossible. Never rebuild that dict at a call site; if you add a product widget, adding it to `read_products_selection` is the whole change.

  **A drafted line may carry its own `cpm`, and an override always announces itself.** Rates are negotiated per deal, so a line's optional `cpm` overrides the rate card default from `line_product_spec`; omit it and the default applies (which is what "hold sports at rate card" should produce — an *absent* field, not a copy of the default). `_resolve_line_cpm` falls back to the default on anything non-numeric or ≤ 0 rather than pricing a rate line at zero, and every case emits an `unresolved` note, because nothing downstream distinguishes a negotiated rate from a standard one and a silently cheap CPM is a mispriced proposal. A `custom_fee` line has no rate at all — a `cpm` on one is ignored and flagged. The clarify round can set or clear rates too ("drop Premion to $28"), and its rules say outright that a rate change touches `cpm` while a budget change touches `total_budget`, since the two are independent and Python re-derives impressions from both. Note `unresolved` is deduped on the way out (`dict.fromkeys`): options are variants of one plan, so a per-line note fires identically per option and the reviewer should read it once.

  **A stated budget must never come back with zeroed rows.** Every option carries its own `total_budget` and resolves its allocations independently against it; an option with lines but no budget can only produce $0 rows, which then all trip the $0-line drop and take the option with them. That used to surface as a bare "one or more options had no usable lines". It now names the option and says the budget was missing (or, when only fixed-amount lines could be priced, that everything sharing a remainder was dropped), and the prompt states that every option MUST carry its own `total_budget`. Relatedly, a budget **range** with no split instruction ("between 50 and 75, wants to see both") defaults to one option per stated figure, each holding that figure.

  **A re-draft is merged over the previous draft, because a dropped field isn't neutral.** The model is told to return the whole object, but it dropped `agency_involved` on a revision once — and a missing boolean doesn't read as "unchanged", it reads as "no agency", which silently repriced every line at net instead of gross (a $37,500 line came back as 568,182 impressions, i.e. 37500/66, where it should have been 494,071 at 37500/(66×1.15)). `call_claude_redraft` now returns `{**previous_draft, **revised}`, so anything the revision omits keeps its prior value while anything it returns still wins. Relatedly, when a section is being skipped because the user hand-edited it, values that feed derived math are read from the **form's** state rather than the draft's own field — pricing rows off a skipped `agency_involved` would contradict the toggle sitting right there on screen.

  For drafting, Claude returns the whole media plan as `media_plan_lines` — one entry per intended **row**, not one per product (the same product can appear on multiple lines with different `label`/`audience_track`, e.g. a Commercial vs. Retail split, each becoming its own row with the label appended to the tactic name). Each line's `allocation` is exactly one of `flat_amount`, `percent_of_total`, `percent_of_remainder`, or `split_evenly`; `apply_draft_to_form()` resolves them as a waterfall — flat amounts and percent-of-total first, then percent-of-remainder out of what's left, then `split_evenly` divides whatever remains evenly across those lines — and only then computes impressions = amount ÷ (CPM × markup) × 1000, reusing the same `PRODUCTS` CPM table and cost formula the rest of the app already uses. A line can also use the special product value `custom_fee` for a one-time flat fee unrelated to any real media-buy product (e.g. a production/creative fee), using its `label` as the tactic name directly. Any audience segment Claude names (in the separate `audiences` array, for the avails table — distinct from a line's free-text `audience_track`) is checked against the real catalog via `validate_segments()` — unmatched names are dropped with a note in `unresolved`, never silently kept. Draft values are written into `st.session_state` keyed to each widget *before* that widget renders, followed by `st.rerun()` — Streamlit raises if you assign to a widget's value after it's already instantiated. Sections touched by the last draft show a small badge caption that clears via each widget's own `on_change` the moment the user edits anything in that section.

### FLOW_REWORK_PLAN.md Phase 3 — entity identity, and three corrections that came from live plan review

- **Entity is a join key (`entity_id`), never the Label text a rep can freely rename.** The plan doc's original design considered joining avail rows to plan lines on the Label string itself; it was overruled during implementation review specifically so renaming "Toyota" to "Toyota of Annapolis" can never orphan the rows it used to match or silently regroup two entities whose new names happen to collide. `entity_id` defaults to a group's own `id` (so an ungrouped group needs no special-casing anywhere), and `entity_label` is purely display — `targeting_groups.entity_id_of`/`entity_label_of` are two different accessors on purpose.
- **The plan doc's original "not a new column — reuse the existing Label" line was already stale before this phase was built**, and the Annapolis Cars document is exactly why: one entity (one make) sells as TWO avail rows, a 5mi and a 10mi radius tier around the same origin zip, needing two *different* Geo-cell overrides (`name`/`geo_label()`) but one shared entity name. Reusing one field for both jobs doesn't survive that case — a new `entity_label` field was added, the D2 grid's existing Label column (the Geo override) was renamed **"Geo Label"**, and the new column took the bare "Label" header. `FLOW_REWORK_PLAN.md`'s own Phase 3 section carries a superseded-and-corrected note rather than being silently rewritten, so a future reader who half-remembers the old design isn't steered wrong twice.
- **No automatic row collapse — this overturned the plan doc's original design during live review, not before it.** The original plan had rows sharing a Label merge into one plan line automatically, taking the larger of the avails figures. The corrected rule: **one ticked avail row is one plan line, always** — an entity spanning several rows (alternate radius tiers, two locations of the same brand) is a legitimate multi-line plan shape a rep may want to keep, not an error the app resolves on its own. Collapsing stays a rep action through the existing `merge_plan_rows` control, unchanged by this phase. The corrective case: a rep who wants Denver's 5mi core priced separately from its 10mi ring must be able to keep both lines — silent auto-merge would have destroyed a plan shape that real sellers use.
- **Max-within-entity, sum-across-entities is scoped to a row's own already-selected `_group_ids`, never to "every group sharing this entity_id."** Because rows never auto-collapse, the only way a row ever carries more than one group id is a rep's own merge action — so `matched_avails_for_row`/`matched_avails_full_flight_for_row` bucket by `tg.entity_id_of` over the row's live membership only, max within a bucket, sum across buckets. `entities_of`/`entity_avails_monthly` are deliberately built to take an already-selected list as their argument, never the raw full group roster — calling either with "every group under this id" instead of "what's actually ticked/merged onto this row" was flagged during design as the exact bug this scoping rule exists to prevent (an untouched 10mi sibling leaking into a 5mi-only line's figure).
- **Per-entity allocation divides by distinct entity count, not row count — and the entity's one computed figure lands on exactly one row.** "Split evenly across the four stores" divides a stated budget by 4 entities in Python, never by however many avail rows sit behind them; each entity's own waterfall result applies to the first selected row for that entity in stable order, and any other selected-but-unmerged row for the same entity is left at whatever it already had (typically its seeded $0). This asymmetry is deliberate, not a bug — an entity with an unpriced sibling row is exactly what the allocation-basis caption (below) exists to surface, so it never looks like a silent mistake.
- **A stated dollar figure always outranks an inferred avails percentage for the same entity — a deterministic, prompt-level precedence rule, never left to which the model happened to emit.** The rule was never "no dollar figures in notes-driven allocation" — it's "never invent one." Dividing a *stated* $15,000 four ways is arithmetic on a number the notes actually gave; producing a plausible budget from nothing is what stays forbidden. When notes support both readings for one entity, the prompt instructs the dollar-figure reading to win, and a dedicated test (a synthetic notes string stating both) asserts that resolution rather than trusting the model to be consistent about it.
- **No new "budget split %" column — a read-only caption instead, because a percentage column is a second display owner for a number the Cost column already shows.** The alternative was raised and rejected during review: a rep reading "25%" next to a Cost figure that says otherwise (because the row was hand-edited since) is worse than showing no percentage at all — the two values would drift, and drift in a client-facing number is the failure mode this whole rework exists to avoid. What's actually invisible is the allocation *basis* (did this figure come from `split_evenly`, a stated flat amount, or `percent_of_avails`?), not the amount — so `describe_group_allocation` renders one plain-language caption under the plan table, derived strictly from the draft's own stored `group_allocation`/`group_entities` intent, **never back-computed from the rows' own Cost figures**, and it drops or qualifies its claim the moment a rep hand-edits any row it would otherwise describe.
- **Deterministic entity inference at avails-PDF import time (`avails_pdf_import.infer_entities`) is scoped to two verified structural patterns, not a general segment-name matcher — and it says so where it falls short.** R1 (nested geography: same audience term-set and radius origin, differing radius) is verified against the real Annapolis document — 8 rows collapse to 4 entities. R2 (nested audience: identical geography, a DEMO age bracket narrowed by gender over the same range) is verified against the real Plaza Motors document — 2 rows collapse to 1 entity. **The local audience catalog was checked and confirmed to carry no other "DEMO Age" bracket family beyond Plaza's own case** — R2's scope is deliberately limited to the one real pattern verified to exist, rather than a guessed general rule, an explicit honesty choice recorded in the function's own docstring. Wilmington University's 3 undergraduate-audience rows share no structural fact either rule can key on (no shared term-set, no shared bracket family) — the deterministic pass correctly leaves them ungrouped and emits one aggregate `unresolved_internal` note for the whole document rather than fabricating a tie between them. That's what makes drafting's own `group_entities` key (below) necessary rather than redundant: it's the only mechanism able to name an entity from context the parser structurally can't see.
- **Drafting can name entities `group_entities` cannot invent a merge — assigning `entity_id`/`entity_label` never merges rows, mirroring the no-auto-collapse rule above exactly.** A model-drafted `group_entities` entry (`{"label": ..., "match": [...] | "ids": [...]}`) resolves through the same `match_groups_to_selection` selection mechanism `group_selection` already uses, and only ties groups that are neither `entity_locked` (a rep's own edit) nor already grouped by the deterministic pass — rep edits and deterministic inference both outrank the model. Wilmington's 3 undergrad rows, once labeled by a draft, still render as 3 separate plan lines by default; combining them into one is still the rep's own `merge_plan_rows` click. Treating drafting as a carve-out from "collapsing is a rep action" — just because it's an automated caller rather than a human clicking a button — was considered and rejected for consistency with every other decision in this phase.

### The LiveWell deck review (2026-09-01) — labels can NAME without merging, color-by-entity was tried and declined, and a real geo-resolution bug was found underneath both

Generating a real LiveWell deck and reading it as a proposal, not just checking it parsed, surfaced four separate things. Two shipped, one was declined with its reasoning recorded, one turned out to be the session's real find.

- **`group_entities` and `apply_draft_group_entities` both had a hidden assumption: an entity always spans 2+ rows.** Wrong for LiveWell's actual shape — seven locations sharing one audience ("LIFESTYLE Pets"), already correctly SEPARATE (`group_entities: null`, right where it stood), but each one still deserving a real name so the Targeting column doesn't read identically seven times. The prompt's own instruction and examples were 100% about merging (`{"label": "Toyota of Annapolis", "match": ["Subaru"]}`) — nothing told the model naming a single, already-distinct row was even a thing this field could do. And even if the model had tried: `apply_draft_group_entities` had a hard `if len(matched_ids) >= 2:` gate, with a docstring saying so explicitly ("a 'match'/'ids' list resolving to fewer than 2 groups groups nothing — there's no entity to form from one row"). Both fixed: the prompt now names both jobs (`group_entities`'s docstring here has the exact wording); the Python gate now has a `len(matched_ids) == 1` branch that sets `entity_label` alone, `entity_id` untouched (the row already IS its own entity by construction) — naming, not merging, structurally can't reshape anything else. Guard: `tests/test_entity_label.py`'s "Solo C" case.
- **A deterministic parser covers what the prompt can't reach for free — `avails_pdf_import.infer_entity_labels`, checked against geo-name formats across all real documents on hand before writing a line of it.** Formats vary too much for one universal rule: DMA kind is already a clean label (`"Philadelphia"`, used verbatim); Annapolis's bracketed-zip radius (`"10mi radius [21401]"`) and Wilmington/Plaza's identical-across-every-row strings have no place name in them at all to extract, and correctly return `None` — audience already tells those rows apart, which is exactly why nobody needed this before LiveWell. Only a real street address (LiveWell's own shape) has anything extractable: the city is the text between the last recognized street suffix (St/Ave/Blvd/...) and the trailing STATE+ZIP, with a leading directional token stripped. **The critical case: three of LiveWell's own seven rows are all in Washington DC on different streets, and city-only extraction makes all three reduce to the identical string "Washington."** `infer_entity_labels` drops a label from EVERY row it collides on, not just the extras — a wrong-but-confident label reading as "these are the same place" to a client is worse than three blank Label cells inviting a rep to type the real names in. Deliberately does not fall back to the full street address when the city can't be cleanly isolated, either — a raw address is exactly the content a plan-table label must not carry, the same rule `geo_label()` already follows for the Geo cell. A separate, narrower gap was found in the same investigation and deliberately NOT touched here: `classify_geography`'s own `radius_origin` extraction (`_BRACKET_ORIGIN_RE`) only recognizes a bracketed origin, so LiveWell's unbracketed street addresses never reach real radius-mode geocoding at all — they resolve through the document's own stated zip list instead. That's a judgment call (re-geocode vs. keep the document's own priced footprint), not obviously a bug, and BACKLOG.md carries it separately so it doesn't get bundled into label-parsing work that doesn't need it. Guards: `tests/test_avails_pdf_import.py` (the pure parser, including the Springfield/Springfield collision case built specifically to exercise the guard, not just the real documents happening not to trigger it), `tests/test_avails_pdf_wiring.py` (labels reach real `targeting_groups` through the real import, never lock, never merge).
- **"Show Label in plan" gained a computed default, and it's a genuinely different shape than every other lock flag in this file.** `color_locked`/`include_locked`/`entity_locked` all gate a *piece of DATA* a rep edited by hand. This gates a *plain top-level checkbox*, which has no comparison baseline — off-by-default and off-because-a-rep-declined are the same stored value, `False`, so nothing can tell them apart after the fact. The fix is a ONE-SHOT firing, not a continuously-reasserted default: a `show_entity_label_suggested` flag that's checked fresh every render (cheap — `audience_label`/`geo_label` are already computed per group) but only ever WRITES once, the first render on which 2+ ticked groups share one audience and 2+ distinct geo labels. After it fires — whichever way it resolves — this code never touches either key again, so a rep leaving it on, or deliberately turning it back off, is respected identically from then on. Checked fresh every render rather than tied to one specific event (an avails import) on purpose: which groups are TICKED can change via several different actions (an import's own "Add all to plan," a draft's pre-selection, a later single D2 tick), not just the import itself, and a fresh-avails-imported group is never automatically ticked — hooking this to import completion alone would have meant it never fires until something ELSE ticks the groups anyway. Guard: `tests/test_show_label.py`, including the three shapes that must NOT fire (one group ticked; two ticked but different audiences, Annapolis's own shape; two ticked, same audience AND same geo, Wilmington/Plaza's shape). **The full sweep, not this feature's own targeted tests, is what caught a real consequence of it**: `test_group_plan_selection.py` started failing with `IndexError: loc must be an integer between -0 and 0` from `media_plan_df.insert(1, "Label", ...)` in `main()`'s own media-plan editor — pre-existing code from when this phase first shipped, but never reachable before, because nothing had ever exercised `show_entity_label=True` together with zero plan rows in the same render. `pd.DataFrame([])` (every group unticked) has zero COLUMNS, not just zero rows, so inserting a new column at position 1 is genuinely out of bounds. The new computed default is exactly what started reaching this combination live (turn it on automatically, then a rep unticks everything). Fixed with one added condition (`and not media_plan_df.empty`) — skipping the insert is correct, not just safe, since there's nothing to label on an empty grid anyway. Guard: `tests/test_show_label.py`'s own zero-rows scenario, proven to catch the exact regression by reverting the one-line fix and watching it fail with the identical message before restoring it.
- **Color-by-entity was proposed, investigated, and declined — recorded here so it doesn't get re-proposed without this reasoning.** All seven LiveWell rows render Blue because the color cascade keys on `audience_label`, and all seven share one audience — genuinely uninformative for this shape. Rekeying to `entity_id` instead was the obvious fix and it degrades safely IN PRINCIPLE (every group defaults to its own entity, so an ungrouped proposal gets one color per row exactly as an all-distinct-audiences proposal already does). Two real problems killed it anyway. First, an ordering bug: `_color_for_new_group` assigns color as each group in `new_groups` is built during avails-PDF import; `infer_entities`' real entity-pairing runs in a SEPARATE, LATER pass over that same list — at color-assignment time, every group's `entity_id` is still its own fresh default, so Annapolis's 5mi/10mi Subaru pair (correctly ONE entity, correctly ONE color today, via audience-matching) would get two DIFFERENT colors under naive entity-keying, a real regression in an already-shipped, already-tested scenario. Fixable, but real re-plumbing, not a lookup-key swap. Second, and decisive: `color`/`audience_cascade_color` is not only a D2-grid concern — it is ALSO `targeting_map.py`'s own legend-collapsing and 2-vs-3-way overlap-hatch key, which exists specifically to answer "which AUDIENCE is targeted where" geographically. Rekeying color to entity would make LiveWell's map show seven different colors for what genuinely is one audience at seven locations — actively worse for the map's own stated purpose, since a client glancing at seven colors reasonably reads that as seven different audiences, not one audience seven places. **The map's audience-keyed correctness is a working, deliberately-designed mechanism (see "Color follows the audience, not the group" in CLAUDE.md's own Status section) and this doesn't get to break it for a D2-grid-only annoyance that the label fix above already solves without touching color at all.** No code changed; this bullet is the whole deliverable.
- **The real find, underneath all three above: `install_market_lookup()` ran AFTER the intake avails uploader in `main()`'s render order — a side effect of the UX sweep moving intake to the top of the page without moving this call with it.** Every zip-originated group imported through intake (the primary, unconditional entry point since that sweep) resolved its zips with no market lookup registered yet; `geo_resolver.zips_to_markets` came back empty, silently, every time — while the SAME document through the D2 entry point (which sits after the old call site) resolved correctly, confirmed by importing the identical LiveWell PDF both ways in the same process. This reaches further than the D2 grid's own Markets column (which was the visible symptom — falling back to `geo_label()`'s text, the SAME string as the Geo Label column beside it, since `_group_markets`'s own documented fallback for "no resolved markets" is exactly that): `apply_group_markets_autofill` reads `resolved_markets` too, to seed `target_dma_choice`, which Campaign Specs Geography and the market-profile slide picker both depend on. **A live query against every real, already-logged proposal found the concrete harm:** of 22 real proposals, 6 showed the symptom (empty `resolved_markets` on a zip-originated group with real `resolved_zips`) — and one, **"Undisclosed Advertiser" / Capital Media, RFPID-266994, generated 2026-08-31 by Matt**, shipped with Campaign Specs Geography reading *"Washington, DC DMA"* (the originating-market fallback) instead of the Baltimore/Salisbury the avails document actually targeted (real Eastern Shore MD zips, confirmed by re-resolving them fresh). The other 5 (including three of the LiveWell/Lawn & Leisure runs from this same review) had no visible harm — a drafted narrative supplied Campaign Specs Geography directly in 4 of them, and the originating market coincidentally matched the true resolved market in the fifth (Plaza Motors, itself in St. Louis) — but the underlying resolution was broken in all 6 regardless of whether it happened to show. Fixed by moving `install_market_lookup()`'s call site to the very top of `main()`, ahead of the intake uploader — `@st.cache_resource`-idempotent, depends on nothing computed in between, a pure reordering. **One more thing this surfaced, worth its own line: `install_market_lookup()`'s `@st.cache_resource` caching is PROCESS-wide, not per-session** — meaning this bug's real-world blast radius depended on which entry point happened to serve the FIRST avails import in a given warm server process's lifetime, not on which entry point any individual rep used. That's also why a revert-and-rerun proof inside `test_avails_pdf_wiring.py`'s own multi-scenario `main()` doesn't reliably reproduce it (an earlier scenario in the same process already warms the cache) — verified as a real bug and a real fix in a genuinely isolated, single-purpose process instead, and the permanent regression guard is a source-order assertion (`inspect.getsource(app.main)`, confirming `install_market_lookup()` textually precedes the intake uploader) precisely because it's immune to that caching effect where a live functional re-test in the same file wouldn't be. Guards: `tests/test_avails_pdf_wiring.py`'s "Both entry points resolve geography IDENTICALLY" scenario (functional comparison + the structural source-order check).

**The tripwire this whole review is evidence for, recorded once already under "A failed Claude call has to say which failure it was" but worth repeating here since it generalized past drafting:** the signal to worry about is repeated LOOKUP misses (wrong or missing segments, geos, markets — losing track of reference data), not judgment misses (an incomplete instruction, a genuinely ambiguous case). Everything found this session was the second kind, including the one buried under three others.

## Case studies

### Cross-deck copying, images vs copied slides, flattening

- **Case studies are grafted in from other .pptx files, and cross-deck copying is much harder than in-deck duplication.** `duplicate_slide` works inside one presentation where every referenced part already exists; `copy_slide_into` pulls a slide out of a *different* file, so every part it references has to be imported and renumbered. Three things the obvious approach gets wrong: (1) **never `get_or_add_image_part`** — it re-encodes through python-pptx's `Image` class, which only understands raster formats and fails outright on the EMF/SVG parts these decks are full of; parts are copied blob-verbatim instead, so any content type survives. (2) **A chart is not a leaf** — it carries its own relationships to an embedded workbook plus colour and style parts, so importing only media leaves charts pointing at nothing; `_import_part` recurses, and rewrites rIds *inside* copied XML parts too (a chart's `<c:externalData r:id>`). (3) **Slide backgrounds live on `<p:cSld>`, outside the shape tree** — copy them separately or a full-bleed background silently vanishes. Copied slides land on the destination's Blank layout (a slide can't bring its own layout across, and a layout full of placeholders stamps stray boxes underneath), and the same `_next_free_slide_partname` collision fix applies as for duplication. One `ImportCache` must span a run of copies: every case study deck ships its own copy of the same PREMION logos, so a per-call cache deduplicated within a slide and then imported identical bytes again for the next one (336 media parts / 15 duplicate blobs, versus 321 / 2 once shared — below the master deck's own baseline of 3, so case study assets dedupe against the master too). The cache is seeded from the destination's existing media for exactly that reason.
- **A case study goes into a deck as images when it has them, and as copied slides when it doesn't.** `append_case_studies` takes either `{"images": [...]}` or `{"path": ..., "slides": ...}` per entry and both routes are resolved in `app.case_study_source`, so generate and rebuild-as-presented can't disagree. The image path exists because cross-deck OOXML copying has produced **five distinct corruption bugs** here and still can't reproduce PowerPoint's live autofit — flattened text renders a line taller than its box and clips on a client-facing slide. A picture has no relationships, theme, layout, placeholders, autofit or embedded parts, so none of that is expressible.

  **It is also smaller, which was the surprise.** Copying drags in the source deck's full-resolution photography; a rendered slide is one flat JPEG. The two furniture case studies cost **+7.83 MiB copied, +1.44 MiB as images at 2560px** (+0.97 at 1920) on a 29.19 MiB base deck. 2560px (~192dpi across a 13.33in slide) is the default: it costs 0.47 MiB more than 1920 and holds up zoomed in and in print. Masters stay at 21 either way.

  **The cost is permanent and is the reason the copy path stays:** an image slide is not selectable, searchable or editable text. A typo means fixing the source deck and re-rendering. Nothing about a proposal changes otherwise — the images are full-bleed on blank slides with `showMasterSp="0"` so the destination master's footer can't draw over them.

- **Case study images are generated locally, never by the app.** `render_case_study_images.py --pending|--all|--list` renders over PowerPoint COM and uploads to the same `case_studies` bucket, recording the ordered object keys in `case_studies.slide_images`. It can't run on Streamlit Cloud: there is no PowerPoint there and no **Proxima Nova**, so rendering there would silently substitute fonts and store images that aren't what the case study looks like — the same substitution hazard `text_metrics` exists to avoid. Empty `slide_images` *is* the pending queue, so there's no separate state to keep in sync: the vault browser marks each row 🖼 images or 📄 copied and the upload flow says outright that a new case study needs generating and how many are waiting. `image_width` and `images_generated_at` are recorded so a re-render at a different resolution is identifiable.

  **Two hands-off ways to run it, both safe to leave unattended.** `render_pending.bat` is the double-click: it `cd`s to its own folder (`%~dp0` — a shortcut otherwise starts in `System32` and every relative path is wrong), picks a project venv if one exists, runs `--pending`, prints a summary and `pause`s so the window doesn't close before you've read it. **To pin it:** right-click → *Show more options* → *Create shortcut* (a `.bat` can't be pinned directly, but its shortcut can) → right-click the shortcut → *Pin to taskbar*, or drag it to the desktop. `schedule_render_pending.ps1 -Register [-At 08:30]` registers a weekday Task Scheduler job; `-Status` reports the last result and next run, `-Unregister` removes it.

  **What makes it safe to schedule** is that each guard exists for a failure this project already hit. `--skip-if-busy` does nothing when PowerPoint is open, because a COM `Dispatch` **attaches to a running instance** — so quitting afterwards would close the window you're working in (`deck_render.render_deck` now quits only an instance it started, for the same reason, and see the never-force-kill-a-GUI-app rule). A modal dialog in that window also blocks every COM call outright. `--quiet` and the "nothing to do" early return mean a job that finds no pending case study leaves nothing but a log line — the point being that it never interrupts. The task runs `LogonType Interactive`: "run whether logged on or not" would launch PowerPoint in a session with no display and hang. Exit codes are the scheduler-readable result — `0` ok or nothing to do, `1` something failed, `2` couldn't run — and every run appends to `deck_render.render_root()/render_case_study_images.log`, including the runs that did nothing, because "did it even fire?" is the first question asked of a scheduled job.

- **A copied case study slide inherits nothing, because it is flattened on arrival.** A slide grafted from another deck lands on the destination's Blank layout, so everything it *inherits* rather than states is silently reinterpreted: placeholder sizes come from Premion's master, `<a:schemeClr val="tx1"/>` and `typeface="+mj-lt"` resolve against Premion's theme, and brand-white headings render near-black. **18 of the vault's 22 case studies are placeholder-based**, so this was the common case, not an edge one — the four that were fine are built entirely from explicit TextBoxes, which is why the chart-import work never surfaced it. `slide_inheritance.flatten_inherited_formatting` resolves the inheritance and writes it onto the shapes: placeholder geometry, body properties (including the autofit element, which is a *child* not an attribute), run properties, paragraph properties (including `lnSpc`, a child too), then scheme colours through the source `<p:clrMap>` and theme fonts through its `<a:fontScheme>` — **colours and fonts last**, since the inherited defaults themselves contain those references. It then strips `<p:ph>`, which requires two follow-ups that are easy to miss: a de-placeholdered `<p:sp>` **or `<p:pic>`** has no geometry, so an explicit `prstGeom` is added (without it the case study's cover photo sat in the file at the right size drawing nothing, and python-pptx refuses to type the shape at all — `slide_map.iter_all_shapes` now tolerates that); and the layout's and master's own shapes and background are copied in behind the slide, with `showMasterSp="0"` set so the destination's footer doesn't show through. Placeholders are skipped when copying that backdrop (an unfilled one is a prompt, not content) along with date/slide-number fields and confidentiality lines.

  **The faithful alternative was built and abandoned, and the reason is worth keeping.** Importing the source layout, master and theme and pointing the copied slide at them produces a package that is internally consistent by every available check — every relationship resolves, no dangling rIds, correct content types, the master XML byte-identical to its source apart from rIds, layout ids renumbered against collisions — and PowerPoint refuses to open it regardless. Importing a deck's *own* master back into itself reproduces it, so it is not about case study decks. Unexplained; don't retry it without new information.

  **One residual, reported rather than hidden:** PowerPoint recalculates `<a:normAutofit>` only on *edit*, and a flattened shape is no longer a placeholder, so text the source deck's live autofit shrinks can come out a line taller here. `assembly._fit_flattened_text` re-applies the measured fit for shapes that asked for autofit, but it can't reproduce PowerPoint's line-spacing reduction. A blanket safety margin was tried and reverted — it shrank case study titles below the source's own size while still not saving the paragraph it targeted. `tests/test_case_study_import.py` reports the count so a regression shows as the number growing.

### Never key a cache on id()

- **Never key a cache on `id()` when the objects can be collected.** `copy_slide_into` opens its source `Presentation` locally, so every part of it becomes garbage the moment the call returns — and CPython reuses those addresses. `ImportCache` keyed on `id(src_part)`, so a later deck's *style* part could land on the address of a freed *workbook* and the cache would hand back the workbook: a chart came out with two embedded workbooks and no style part. It took four case studies before an address happened to be recycled. Now keyed on `(id(part.package), partname)` **and** the cache retains each source presentation so the identity can't churn underneath it. **Deduplication is also limited to `/ppt/media/`** — it used to cover any part without relationships of its own, which swept in a chart's embedded workbook, and two charts sharing one workbook is a file PowerPoint refuses (the workbook is the copy that chart edits). Images are genuinely shareable and are the reason the cache exists: every case study deck ships its own copy of the same PREMION logos.

  **Both failures were invisible to every structural check.** python-pptx opened the deck, every relationship resolved, no partname was duplicated, `package_check` was clean — and PowerPoint said only "could not open the file". That asymmetry is why `tests/render_scenarios.py` treats a failure to open as a test failure, and why `package_check.check_package` runs in the fast suite on every deck it builds: one catches what can be expressed, the other catches what can't.

## Streamlit mechanics

### A docstring that isn't the first statement

- **A docstring that isn't the first statement is not a docstring — it's copy on the page.** Streamlit's magic rewrites any bare expression into `st.write()`, and `magic._is_docstring_node` exempts a string only at `node_index == 0` of a module, class or function. Adding the test-mode early return above `check_identity`'s docstring silently demoted it, and several paragraphs of internal design rationale ("Not authentication — the password is the gate…") rendered at the top of the login screen for every user until someone read it. Nothing failed and no test noticed, because every other suite sets `authed`/`current_user` and skips both entry screens. Rationale that sits below any code now lives in `#` comments, which nothing can render. Two guards, deliberately at different levels: `tests/test_no_stray_magic.py` applies Streamlit's own rule by AST across every module that imports it (free, offline), and `tests/test_entry_screens.py` renders the login and identity screens through `AppTest` and asserts the **whole inventory** of visible copy, so a stray `st.write` or debug caption fails too rather than only the one string that got out. Those two screens can't be driven through a browser — the password is in the fenced-off `secrets.toml` and test mode bypasses both — which is exactly why they had no coverage.

### The Build form outlives page navigation

- **The Build form outlives page navigation, because Streamlit collects widget state and non-widget state alike is untouched.** Switching to the Audience finder and back used to destroy the form — measured: **111 widget keys gone** (client name, vertical, market, flight dates, every product toggle, every Campaign Specs field) while the **14 non-widget keys survived** (`plan_options`, `avails_seed_rows`, `broadcast_schedule`, the drafted review lists). That asymmetry is the whole bug: Streamlit garbage-collects the session_state entry of any *keyed widget* not rendered during a run. It made the finders unusable mid-proposal — the one workflow they exist for. `snapshot_form_state()` mirrors the form into `_form_state_backup` (an ordinary key, never collected) after every widget on the page is instantiated and *before* Generate does anything, so a snapshot survives whatever Generate raises; `restore_form_state()` puts it back at the top of the Build render. **It restores only keys that are ABSENT**, which is what makes it safe to sit alongside the draft and rehydration paths that write widget keys directly — a live value is never overwritten by a stale one.

  **Three classes of key must never enter the snapshot, for three different reasons.** (1) Streamlit **raises** when a button, download button, file uploader or form has its value set through session_state — restoring one doesn't degrade, it takes the page down. This bit immediately: adding `key="logo_upload"` so the logo machinery could see the uploader put it straight into the snapshot, and returning from the finder raised. (2) A `data_editor`'s stored value is its **edit delta, not its data** — the grids rebuild from `plan_options`/`avails_seed_rows` anyway, and replaying an `added_rows` delta over rows that already contain the addition duplicates the line. (3) `page_choice` is the navigation itself. A fourth, found by the guard rather than by reasoning: **another page's widgets are still in session_state during a Build run** — 96 History keys were measured riding along — so `hist_` is excluded wholesale. `tests/test_form_state.py` walks the AST for keyed widgets of the unsettable types, builds a *representative* key for f-string keys (`f"{row_id}_save"` → `"<x>_save"`) and asks `app._persistable()` about it, so the exclusion list is checked against the source rather than against anyone's memory — the same enforcement style as `test_no_stray_magic`.

  **The client logo needed its own answer**: an uploader is exactly the widget that can't be restored, so its bytes are kept beside it in `uploaded_logo` and generate prefers those over `restored_logo_path`. Without it, walking to the finder and back silently reverted the cover to the placeholder — the failure `logo_used` exists to distinguish elsewhere. The Wide Orbit schedule needed nothing: `broadcast_schedule` holds the *parsed* object under a non-widget key and already survived.

  **"New proposal" clears by deny-list** — everything except `page_choice`/`authed`/`current_user`/`identity_skipped` — because listing what to *clear* is the shape of bug this project keeps paying for, and the symptom here would be a "new" proposal quietly carrying the last one's dirty rows or seed keys. Its confirm is **inline, deliberately not a `st.dialog`**, and that was measured both ways: a modal's "x" leaves the arming flag set so it reopens and Cancel becomes the only way out, while clearing the flag inside the dialog makes `AppTest` unable to reach its buttons at all (dialog fragments aren't re-executed), which would ship a destructive action untested. Inline costs a little polish and keeps both.

### Mechanical isn't the same as safe when a change moves WHERE code runs, not WHAT it does

- **Two incidents in the same rework, both from moving a call site rather than changing its logic, both silently breaking a real proposal's Campaign Specs Geography.** `install_market_lookup()`'s move to the top of `main()` (the UX sweep, above) and the Campaign Specs hoist (2026-09-04, "Move Campaign Specs to directly under Draft from notes") are the same shape of bug from two different directions: the first moved a *dependency* later than something that needed it; the second moved a *consumer* earlier than something it needed. Both were reviewed and described, honestly, as small — "a pure reordering," "a handful of lines, not a redesign" — and both were exactly that, line-count-wise. Neither review caught the break, because the diff really was small; what changed was execution ORDER, and a diff's size says nothing about how many other things silently depended on the old order.
- **The Campaign Specs hoist specifically:** moving `apply_geography_autofill`'s call earlier meant it now had to read `target_dma_choice` from `session_state` directly, since Section A's own Target DMAs widget hadn't rendered yet at that point in the script. That part was reasoned through carefully and correctly. What wasn't checked: `market_profile_picker` doesn't merely *read* that session_state key, it **converts** it — the multiselect's own stored value is a list of display LABELS, and the function returns KEYS, via an internal `label -> row -> key` lookup. The hoisted code skipped that conversion and passed raw labels into a function that expects keys, which silently resolved to nothing for every real market pick. The unit-level reasoning ("session_state already holds whatever the widget would return") was subtly wrong: it's true for a plain value, false for anything a widget *transforms* on its way out. Fixed with `target_dma_keys_from_session`, a shared helper — see the fix commit's own message for the full trace.
- **Neither bug was caught by the review that shipped it — both were caught later, by a full sweep hitting one specific end-to-end test each time** (`test_avails_pdf_wiring.py`'s "both entry points resolve identically" scenario for the first; `test_avails_seeding.py`'s "through the real form" scenario for the second). Both of those tests share the same property: they drive the real widget and assert a real downstream computed result, not a hand-picked argument standing in for what the widget would have produced. See "Which sections have that kind of coverage and which don't" for how thin that protection actually is across the rest of the page.
- **The rule to carry forward: when a change's whole POINT is to move code earlier or later in the script — a hoist, a reorder, "call this before/after that" — review it by asking what the code AT THE OLD SPOT was relying on implicitly (a prior call's side effect, a widget having already transformed its own input) that the new spot doesn't get for free, not just by re-reading the moved code in isolation and confirming it's still correct on its own terms.** A line-count-small diff is not evidence of a small blast radius when the change is about order.

### An AppTest failure that isn't a production bug: session_state set before `.run()`, shadowed by a stale widget-states proto

- **Verified against Streamlit 1.60.0 — re-verify this whole entry against the current version before trusting it after any Streamlit upgrade,** since the argument below rests on `runtime/state/session_state.py` internals (`on_script_will_rerun`, `_compact_state`, `set_widgets_from_proto`) and `commands/execution_control.py`'s `RerunData` construction — none of it public API, all of it free to change silently in a point release.

  **The symptom:** in `tests/test_form_state.py`'s `check_navigation()`, setting `at.session_state["client_name"] = "Ridgeline Heating & Air"` and `at.session_state["wo_upload_path"] = <fixture>` before the *same* `.run()` call made `client_name` revert to its default. Splitting them into two separate `.run()` calls (`client_name` first, the Wide Orbit fixture injected in a later, separate run) fixed it.

  **The mechanism:** `on_script_will_rerun()` — which compacts `_new_session_state`/`_new_widget_state` into `_old_state` and then reasserts `_new_widget_state` from a `WidgetStatesProto` via `set_widgets_from_proto()` — only runs when `rerun_data.widget_states is not None`. `st.rerun()`'s own `RerunData` (`execution_control.py`) never sets `widget_states`, so an *internal* rerun never triggers that compact/reassert cycle — only a rerun carrying real frontend data does. The failing test set `client_name` directly on `session_state` *before* calling `.run()`, while a widget for `client_name` already existed from an earlier run (so `get_widget_states()` captured a stale, pre-override snapshot). That outer `.run()` call's own `on_script_will_rerun` compacted the override correctly into `_old_state`, but immediately re-asserted the *stale* pre-override value into `_new_widget_state` from that snapshot — and because the Wide Orbit upload fires an internal `st.rerun()` before Section A (and `client_name`) ever renders, nothing in that second, internal pass could re-run the compaction and pick the override back up.

  **Why this can't happen in a real browser session, not just "didn't reproduce there":** the shadowing needs an override to land in `_new_session_state` *before* a widget-states-bearing compaction runs. In production, every in-script `st.session_state[key] = value` write necessarily happens *after* that script pass's own compaction already ran (compaction happens once, up front, driven by whatever frontend event started the pass) — there is no path for app code to write a value and then have an *older* compaction reassert over it. `AppTest`'s `at.session_state[k] = v` before `.run()` is unique in letting a caller poke state from *outside* script execution, which is the only way to get the override in before the stale-snapshot compaction runs. **Conclusion: this is an AppTest-only artifact of how `.run()` sequences pre-seeded session_state against `get_widget_states()`'s stale snapshot, not a production bug** — no `app.py` change was made; the fix is in the test's setup sequence. The one place in `app.py` with the same *shape* (a widget-owned key, written in-script, immediately followed by `st.rerun()`) is `draft_notes_input` in the notes-upload block — see the comment there for why the ordering keeps it safe in production, for the reason above.

### A raw list-of-dicts value nested inside a `targeting_groups` entry breaks Streamlit's own widget bookkeeping — confirmed by direct bisection, not fully root-caused

- **Found building FLOW_REWORK_PLAN.md Phase 2's avails-import freeze**, testing against the real 12-group Visit Hershey & Harrisburg document (`tests/test_avails_pdf_wiring.py`). The original design stored each group's avails-PDF `AvailsPeriod` rows verbatim on the group as `avails_periods`, a Python list of small dicts (`{"start", "end", "impressions"}`), for the divergence check (`avails_flight_divergence`) to read later.

  **The symptom:** importing Hershey, then any later rerun of the SAME AppTest session (an untouched rerun, "Add all to plan," anything) crashed inside Streamlit's own `get_widget_states()` — not inside `app.py`, and not reported as `at.exception` — with `KeyError: 'st.session_state has no key "geo_mode_<gid>"'` for one of the per-group geo-definition expander's own radio widgets, which carries an explicit, stable `key=f"geo_mode_{gid}"` and had rendered without issue on the previous run.

  **Bisection, each step confirmed against the real document, not a synthetic one:**
  1. Fully neutralizing the divergence-panel UI (monkeypatching `avails_flight_divergence` to always return `[]`, so zero new buttons/warnings ever render) — **still crashed.** Rules out the new buttons.
  2. Removing the D2 "Avail dates" display column entirely — **still crashed.** Rules out the new column.
  3. Removing the `target_dmas` market autofill (so there's no placeholder group to drop on import) — **still crashed**, and the crashing `gid` was confirmed to be one of the 12 real imported groups, not a placeholder artifact.
  4. Storing every new field EXCEPT `avails_periods` (the simple scalars — `avails_doc_start`, `avails_doc_monthly`, etc.) — **passed.**
  5. Storing `avails_periods` but always as `[]` — **passed.**
  6. Storing the REAL, populated `avails_periods` list (one dict per group, real content) — **crashed**, reproducible on a plain untouched rerun with no Add-all, no divergence match (the document's May–July window doesn't even overlap the test's forced Sep–Nov flight, so the divergence check itself was a no-op every time).
  7. Storing the identical data serialized as a JSON **string** instead of a raw list — **passed** in isolation (a single fresh `AppTest` instance), but the crash returned once three or four OTHER, unrelated `AppTest.from_file()` instances had already run to completion earlier in the same Python process (exactly `test_avails_pdf_wiring.py`'s real scenario order: `at2`/`at2b`/`at3`/`at4` before the Hershey `at6`) — reproducible even with `at6` moved to run FIRST, provided the JSON string held real (non-empty) content.

  **Conclusion, stated at the confidence the bisection actually supports:** a collection value (list-of-dicts, and evidently a sufficiently "real" JSON-string encoding of one) nested inside a `targeting_groups` entry — itself one dict in a list of dicts sitting in `st.session_state` — reliably confuses Streamlit AppTest's internal widget-identity tracking for OTHER, unrelated, explicitly-keyed widgets rendered later in the same script, across a rerun. This was **not** traced to a specific line in Streamlit's own source (unlike the entry above, verified against `session_state.py` internals) — the bisection identifies the trigger precisely without explaining the mechanism. Given real production groups from real avails documents (Hershey: 12 groups) reproduce it, and the accumulation-across-instances behavior suggests something more persistent than a single script run's own bookkeeping, this is treated as a real hazard rather than a pure test-harness curiosity — **don't nest a list or dict value inside a `targeting_groups` entry** until this is understood better or a Streamlit upgrade is verified to have changed it.

  **The fix taken:** don't store the nested structure at all. `avails_flight_divergence` derives the document's implied per-month ranges from the two already-scalar fields (`avails_doc_start`/`avails_doc_end`) via `flight_month_ranges` — the exact same clipping `default_month_range` already does for the plan's own flight — rather than reading the avails-PDF parser's own per-row `AvailsPeriod` list. This is lossless for every real document on hand: a document's own periods are always exactly its overall window clipped to each calendar month (confirmed against Capital Media's four rows, which match this derivation exactly). `AvailsGroup.periods` (added in commit b7b3715, "Phase 2 prep") stays a real, tested part of `avails_pdf_import.py`'s own parser output — this finding is only about NOT round-tripping that list through `targeting_groups`/`st.session_state.groups`, not about the parser being wrong to produce it.

### The divergence check is genuinely per-month despite storage being an aggregate — how, exactly

- **Storage never holds a per-month figure — `avails_monthly`/`avails_full_flight` are the group's whole-document aggregate, and stay that way.** So when a rep asks "which month diverges," the answer can't come from a stored number; it comes from comparing two DATE WINDOWS clipped the same way. `avails_flight_divergence` takes the group's `avails_doc_start`/`avails_doc_end` (the document's own overall span — for Capital Media, 9/21–12/20) and calls `flight_month_ranges(doc_start, doc_end)`, the identical function that clips the *plan's* own flight into per-month ranges elsewhere. That produces the document's *implied* per-month ranges — Sep(21–30), Oct(1–31), Nov(1–30), Dec(1–20) — without ever reading a single per-row figure. Comparing each of the plan's own active per-month ranges against the matching entry from that derived set is the whole check.

  **Why only the FIRST or LAST month of a shared-start window can ever diverge, and why that's not a coincidence:** clipping a window to a calendar month only touches that month's own boundary — a month fully inside the window is never touched by clipping at all, so two windows that agree on everything except where they END produce byte-identical clipped ranges for every month except the one containing that endpoint. Capital Media's document window and the walkthrough's plan window (Phase 2's standing fixture, 9/21–12/14 vs. 9/21–12/20) share the same START, so September through November clip identically in both — genuinely matching, not merely reported as matching — and only December, which contains the one date the two windows disagree on, ever can. A pair of windows differing at BOTH ends would show exactly two candidate months, never more, for the same reason.

  **This was confirmed against a real, live-clicked run, not just the pure function**, after the user asked specifically whether the notice derives from real per-month boundaries or is quietly firing on the whole-document span — `tests/test_avails_import_proration.py`'s `check_capital_media_divergence_and_adjust` reads the actual rendered `st.warning` text off a real AppTest instance (not a direct call to `avails_flight_divergence`/`format_avails_divergence_note`) and asserts it fires exactly once, naming "Dec 1-14" and "Dec 1-20" specifically — and separately asserts the pure function's own output agrees, so a UI-rendering bug (firing for the wrong reason, or on the wrong month) can't hide behind a coincidentally-matching string.

  **A real bug this stricter test found immediately: the D2 "Adjust to plan dates"/"Use document figure" buttons never called `st.rerun()`.** Every other queued D2 action in this codebase ("Add all to plan," the color cascade) calls `st.rerun()` right after queuing, because `apply_pending_avails_plan_adjust()` runs at the TOP of D2, before this panel — queuing from inside the panel and waiting for Streamlit's own next natural rerun would show a stale figure for one whole render, and in AppTest a single `.click().run()` shows no change at all (the queue gets set, but nothing consumes it until a rerun that never comes without a second `.run()`). The original version of this test used `at.session_state["_pending_avails_plan_adjust"] = {...}` followed by one `.run()` — which sidesteps the missing `st.rerun()` entirely, since writing straight to session_state already has the pending flag in place *before* the apply function runs, whether or not the button itself would have triggered a rerun. That's exactly why testing the pending-queue shortcut instead of a real `.click()` missed this: the shortcut is a valid way to test what the apply function does, but not whether the BUTTON actually gets you there.

### `test_targeting_map.py` ran pathologically slowly, inconsistently — found by the full sweep's first real run; root-caused and fixed 2026-09-03

- **`tests/run_all.py`'s very first complete run (61 files) found a genuine, pre-existing defect unrelated to whatever prompted building the sweep** — exactly the kind of thing a curated list of "suites that looked relevant" would never have surfaced. `test_targeting_map.py`, run standalone with no other change in flight, took long enough to trip a 300s timeout in the sweep; two direct standalone reruns afterward (one redirected to a file, one with `python -u` for genuinely unbuffered output) each stalled for 6+ minutes at wildly different points in the file — one got most of the way through (visible in the `TimeoutExpired` exception's own captured partial output), the other stalled almost immediately, at the very first named-group render (`tm.render_map([named])`, a single group with one zip — trivial by every other evidence in the same file, since unnamed-group renders immediately before and after it in the file are fast).
- **Confirmed as real, ongoing CPU-bound computation, not a deadlock:** `wmic process where "ProcessId=<pid>" get UserModeTime`, read twice a few seconds apart, showed the number climbing (~11s of CPU time consumed between two checks) — so whatever is happening is expensive, not stuck waiting on I/O or a lock. The stalled process was terminated (`taskkill /F` — a headless test-script process, not a GUI app holding unsaved work, so the standing "never force-kill a GUI app" rule doesn't apply here).
- **Root cause, found by profiling the actual test file with `cProfile` rather than re-guessing from the symptom description:** `{method 'draw_lines' of 'ImagingDraw' objects}` — Pillow's C-level line rasterizer — accounted for 204 of 242 profiled seconds across just 3,649 calls. Instrumenting `targeting_map._draw_rings` directly showed why: individual `draw.line()` calls were being asked to draw between pixel coordinates in the **hundreds of millions to billions**. `_projector`'s span computation, `span_x = max(max_x - min_x, 1e-6)` / `span_y = max(max_y - min_y, 1e-6)`, floors at a literal `1e-6` **degrees** — meant only to dodge a division by zero, never intended to stand in for a real span. A near-point group (the common, deterministic trigger: exactly one zip, so `all_lat`/`all_lon` each hold a single value and `max - min == 0`) collapses the span to that floor, driving `scale_x`/`scale_y` (`width / span`) to roughly 9×10⁸ px/degree. `_matching_boundaries`'s own search box is floored sanely (`_MIN_SEARCH_DEGREES = 0.35`, already documented as "a floor for a near-point group (e.g. one zip)") and correctly finds the real, nearby county/state boundaries — but projecting THEIR coordinates through the insane scale flings them to those billion-pixel positions, and Pillow's line rasterizer takes time proportional to that unclipped pixel-space length: 6-10 seconds per `draw.line()` call, dozens of them per affected render. This is exactly the "pathologically slow, CPU-bound, inconsistent point in the file" symptom — the inconsistency was never environmental; it was simply *which* scenario in the file happened to hit a near-zero-span group, and how many boundary features the search box found nearby to fling off-canvas.
- **Fix: floor the projector's span at the same real-world minimum the search box already uses (`_MIN_SEARCH_DEGREES`, cos-latitude-corrected on the x axis), not an infinitesimal epsilon.** A near-point group now renders at a sane, maximally-zoomed-in scale instead of one that makes every nearby boundary explode. Verified by instrumenting `_draw_rings` before/after: 0 calls over 50ms after the fix (previously dozens per run, several seconds each); the full `test_targeting_map.py` file dropped from a documented 6+ minute stall to ~25s, all 105 checks still passing; a single-zip render was inspected visually (correct, tightly-zoomed dot with a legend and nearby state outline, no distortion); and the fix was verified to change nothing else by reproducing the pre-existing, unrelated "map picture sometimes doesn't land on the avails slide" bug (BACKLOG.md) identically on both the fixed and unfixed code via `git stash`, ruling out this fix as its cause. `tests/test_group_scenarios.py --render` (real client documents, through PowerPoint COM) still passes everything except that one pre-existing, separately-tracked bug.

### The same instantiation-order crash was fixed three times as three different fields before it got a name

- **The bug is always the same shape: `st.session_state[key] = value` for a key already bound to a widget instantiated earlier in the same run raises outright.** It surfaced three separate times, at three separate call sites, each fixed as its own one-off before anyone stepped back and asked what they had in common. (1) The avails-PDF importer's own header-field write (`client_name`, from `_avails_import_field`) was the first: D2's entry point tried to write `client_name` directly and broke, since Section A's widget renders before D2 ever runs — fixed with a queue (`_avails_import_pending_fields`, applied at the very top of `main()`, before any widget on the page instantiates). (2) FLOW_REWORK_PLAN.md Phase 6's reorder put a SECOND writer of the same field in play: drafting's own `apply_draft_to_form` wrote `client_name` directly too, and once the setup band moved `client_name` above the Draft button, that write raised the identical error — fixed the identical way, a second queue (`_draft_pending_fields` / `apply_pending_draft_fields`), because the seed-if-empty semantics are genuinely different from the avails importer's (never overwrite once real, vs. flag-not-write) and so needed its own function, but the *mechanism* was already understood by this point. (3) `total_tv` raised the same error days later, found live: `PRODUCT_TO_WIDGET_KEYS`' `"broadcast_tv"` entry writes `updates["total_tv"]` on every draft with a valid plan — not a rare path, a near-certain one — and `total_tv` is a band widget too. Same fix shape again, and by now it was clearly not three unrelated bugs.

  **The fix that actually closes the class, not the instance: `BAND_WIDGET_KEYS`, a frozenset of every session_state key bound to a widget in the setup band, checked generically at `apply_draft_to_form`'s own final apply loop.** Any key about to be written that's a member gets routed into the queue instead of applied directly, automatically — no call site has to know or remember that its own field happens to live in the band. This is the difference between a fix and a *pattern*-level fix: the first two rounds each asked "is this specific field safe to write here," got the specific answer right, and left the next field to fail the same way, because the safety check lived at the call site instead of at the boundary. `BAND_WIDGET_KEYS` moves the check to the one place that can see every write `apply_draft_to_form` makes, so a future band addition, or a future field this function starts writing, is protected before it ships rather than after someone hits it live. **The general lesson, stated for reuse:** when the same category of bug is fixed twice at two different call sites, the third fix should not be a third call site — it should be a set, a registry, or a boundary check that makes every *future* instance of the same category structurally unreachable, not merely the one just found. Two occurrences is a pattern; treating the second one as "just another one-off" is what makes the third occurrence someone's live-testing time instead of a code review comment.
  Confirmed via grep, not by re-deriving the list from memory (this file's own standing rule, CLAUDE.md's "grep, not recollection"): every `updates[...]` write in `apply_draft_to_form` was checked against the band's full widget-key list (`awk 'NR==9872,/st\.header\("A\. Client basics"\)/' app.py | grep -n 'key="'`), turning up exactly the one collision (`total_tv`) and confirming every other write targets a widget in Section A or later — always below the Draft button's own `st.rerun()`, so a direct write there is legal by construction.

### A warm process serving old code — three symptoms, one root cause

- **Local dev:** `import assembly`/`import slide_map` are cached in the running process's `sys.modules`; Streamlit's file-watcher reruns `app.py` on save but does not reload already-imported modules, so an edit to either file is silently invisible until the `streamlit run` process itself restarts.
- **Streamlit Cloud:** a redeploy can reuse a warm process — this took the live app down once with an `AttributeError` on a name whose two halves had always shipped in the same commit. The tempting move (revert) is the wrong one; `git log --oneline -S "<name>"` on each file settles in seconds whether the failing combination exists in any real commit (it doesn't, in this case) — meaning the fix is a reboot, not a rollback. `tests/test_cross_module_refs.py` covers the sibling failure, a genuinely half-complete push, which a reboot does *not* fix.
- **"Verified in tests, reported broken live"** happened twice with the identical shape — a market-lookup registration and a targeting-map slide placement, both landed in real commits, both passing every offline test and a fresh, zero-pre-installed-state `AppTest`, both reported dead in a live session anyway. Same root cause as the Cloud case, presenting as "silently doesn't work" instead of a crash. The fix in every one of these three shapes is the same: restart the process (`python tests/app_process.py restart` for the app_process-managed case) and reproduce again *before* spending investigation time re-deriving that the code is already correct.

## Identity, history and the finders

### Identity is attribution, not authentication; usage stats

- **Identity is attribution, not authentication — and it never blocks.** The shared `APP_PASSWORD` is still the only gate; `check_identity` just asks who's using the app so a proposal, case study upload or attached file can say where it came from. It's a session-level step rather than a field on each form because it's answered once and consumed in three places. **If Supabase is unreachable the step is skipped entirely** (`identity_skipped`), because an unattributed proposal beats a seller who can't build one — verified by running with the table absent, where every page still rendered. The list builds itself: anyone can add a name from the picker and it's there for everyone after, so there's no admin UI (`team_members` is editable in the dashboard if a typo needs cleaning). Deduplication is on a **stored `name_key`** (lower, trimmed, internal whitespace collapsed) carrying the unique index, not on `name` — so "matt", "Matt" and " Matt " are one person while the display name keeps whatever capitalisation was typed first, and a stored column rather than an expression index keeps the conflict target nameable from PostgREST. Adding an existing name returns the existing display name rather than erroring: two people called Matt is the failure worth designing against, and someone re-typing their own name shouldn't look like a mistake. `created_by` on `proposals` is **nullable on purpose** — every row logged before identity existed stays anonymous rather than being attributed to a guess, and the stats page shows those as `—` rather than hiding them. Tests bypass the step by setting `current_user` in `session_state`, exactly as they bypass the password.

- **Usage stats are read-only and computed from what's already logged.** No events table, no new tracking: proposals-per-week over 8 weeks, drafted-vs-hand-built (distinguished by `form_json.draft.notes` already being there), and breakdowns by vertical, market and person, plus a case study count. The question is "is anyone using this, and how", not "what is everyone doing" — anything past one screen would be analytics theater. **Every count has to survive an empty database**, since a new deployment renders this before anything exists; that path is exercised for real right now, and the week bucketing tolerates a null or malformed `generated_at` rather than raising.

### Proposal history is append-only

- **Proposal history is append-only, and reuse never rewrites what a client was sent.** The `proposals` table stopped being capture-only: the History page reads `form_json` back to load a proposal into the form, rebuild the deck as originally presented, or start a new one from an old one. Regenerating a loaded proposal **inserts a new row** carrying `parent_proposal_id` back to its source — nothing is ever updated in place, because a row is the record of what a client actually received. `parent_proposal_id` is `ON DELETE SET NULL`, not cascade: deleting a junk row that a real proposal happens to descend from must orphan the link, never take the descendant. Delete is the only removal, is type-to-confirm, and is deliberately not offered in bulk.

  **Rehydration goes through `read_seed_selections` like everything else.** `rehydrate_proposal_into_form` writes every widget's key before that widget renders, then reruns — the same mechanism as the draft prefill, and subject to the same trap: a hand-rolled `_product_seed_key` that merely omits a key makes `main()` rebuild every option's rows as fresh $0 seeds while leaving the option *names* alone, which reads as "the budget didn't load" and is near-undiagnosable from the symptom. One shared constructor, used by both paths. Restored rows are also marked **dirty**, or the shared-field re-seed would overwrite the very numbers being loaded. Rehydration needed keys added to five previously-unkeyed widgets (`preset`, `tegna_positioning`, `include_vertical_slides`, `include_avails_template`, `proposal_title`, `active_months`) — an unkeyed widget simply cannot be restored.

  **"Rebuild as presented" uses the stored `deck_payload` verbatim and the proposal's own deck version.** Both matter for fidelity: recomputing the media plan would re-price against today's rate card, so a CPM change since would quietly rewrite what the client was shown; and the deck version a proposal was built from is almost always inactive by now, which is why `fetch_deck_version` doesn't filter on `active` and `_deck_file_for_version` caches per version (verified: version 3 fetches and caches independently of active version 4). A case study since removed from the vault produces a warning and a deck without it, never a failed rebuild — and `fetch_case_study` ignores `active`, since deactivation stops one being *offered*, it doesn't rewrite history.

  **The client logo is stored, because an uploaded file isn't part of the recipe.** Without it a rebuild silently used the placeholder, so "as presented" wasn't. It's uploaded to `proposal_files` under a `logos/` prefix on generate and recorded as `logo_storage_path`. Three states are kept distinct, and the difference matters: **no logo** (placeholder is correct, say nothing), **logo stored** (restore it), and **had a logo that can't be fetched or predates storage** (rebuild anyway with the placeholder, but warn that the cover won't match — a deck with the wrong logo beats no deck, as long as nobody thinks it's faithful). `form_json.logo_used` records that a logo was used at all, independent of whether storing it worked, which is what separates the first case from the third. A `st.file_uploader` **cannot** be prefilled from session_state, so a loaded proposal carries its logo as a *path* (`restored_logo_path`) that generate uses unless a new file is uploaded over it. Tier 1's round trip builds with a deliberately distinctive image and asserts its bytes are in both decks — reusing `placeholder_logo.png` there would make a logo that silently fell back indistinguishable from one that survived.

  **`revision_label` annotates the row, never the deck.** It's the one field on a history row that's editable after the fact, precisely because it's a note *about* a proposal rather than a claim about what the client received — `db.update_proposal` allows only it, the logo pointer and the file note, and nothing that describes what was generated. It's offered beside the proposal title at generate time and prefilled with a thread-position default ("Revision N", counted off the client's existing rows) when the build came from Load or Start-new-from, since that's the case where a label is actually worth having. A from-scratch build leaves it blank.

  **Attached final files are the one exception to storing-the-recipe.** A deck is sometimes downloaded, hand-edited in PowerPoint and sent in that state, at which point `form_json` no longer describes what the client saw. Attaching the real `.pptx` (private `proposal_files` bucket, through the same optimize/size-gate path as a master deck) makes the row honest again. Rows with one get a badge, a Download action, and — importantly — **Rebuild as presented warns that the rebuild reflects the pre-edit state** and offers both. These files are also the only thing in the app that isn't regenerable and so the only thing that grows without bound, which is why the History page surfaces the bucket's total usage against the 1GB free tier.

### Both finders have two entry points and one implementation

- **Both finders have two entry points and one implementation.** Reps use them without building a proposal, so Audience finder and Case study finder are pages as well as being embedded (D2 and before Generate). `_audience_finder_body` is the shared component; the proposal flow wraps it in its expander, the page calls it bare. **`avails_df is None` means standalone** — no "Add" buttons, because there's no avails table to add to. The vault browser edits tags inline rather than requiring a re-upload (a mis-tagged vertical is a one-word fix; making someone re-upload 40MB guarantees nobody does), and deactivating keeps the row and file but stops it being offered. **Per-case-study downloads are deliberately not eager**: `st.download_button` needs the file's bytes at render time, so drawing one per row would pull the whole vault (22 files, ~42MiB) out of storage whether or not anyone clicked. `db.case_study_cached_path` reports whether a file is already local — from an earlier click or because a proposal included it — and only those get a button straight away; the rest take one click to fetch first, through the same `@st.cache_resource` download so nothing is ever fetched from Supabase twice.

### Look at the pictures

- **Look at the pictures. `python tests/render_scenarios.py` renders the standard scenarios to PNG and saves the decks beside them** (under `deck_render.render_root()`, printed on every run, outside the repo). Every layout failure this project has shipped was invisible to an assertion and obvious in a rendering: a Comscore footer read as a programme row, a table whose declared height cleared the floor while the rendered one didn't, per-page impressions contradicting their own spot counts. Assertions confirm what someone thought to measure; a rendering shows what's there. It uses **PowerPoint through COM** (`deck_render.py`), not LibreOffice — LibreOffice is blocked by org policy on this machine, and PowerPoint is the better answer anyway since it's the renderer the client will open the deck in. Windows-only; every caller skips when it's absent, and `pywin32` is pinned as a test-only, `sys_platform == "win32"` dependency the deployed instance never installs. Two Windows-specific traps it already hit: don't `rmtree` the output directory (OneDrive holds a handle on a folder it's mid-upload), and retry `Presentations.Open` once (OneDrive can still hold a freshly written 25MB deck). **A deck that python-pptx opens happily can still be one PowerPoint refuses** — that asymmetry is the whole point of rendering.

### Local test mode

- **Local test mode: `PROPOSAL_BUILDER_TEST_MODE=1` skips the password gate and preselects a test user**, so the real UI can be driven without anyone sharing a password. Deliberately hard to switch on and impossible in production: read **only** from the OS environment and never `st.secrets` (which is what a deployed instance actually has, and which someone could set by accident while editing rates), refused outright when the process looks like Streamlit Cloud, and loud on every run it's active. The same flag gates **fixture injection for uploads** — `st.file_uploader` can't be driven by AppTest, so in test mode a session_state path stands in for the Wide Orbit schedule and the Attach-final-file upload, supplying the same `(name, bytes)` a click would. The real widget path is untouched.

### The drafting regression suite, in two tiers

- **Drafting regression suite, in two tiers. Run tier 1 before any push touching drafting, assembly, or the rate card; run tier 2 as well before pushing a change to the prompt, the draft schema, the audience catalog, or the model version.** The split exists because the two halves have completely different costs and failure meanings: one is free, offline and deterministic, the other spends money and is probabilistic.

  **Tier 1 — `python tests/test_draft_regression.py`** (add a fixture-name prefix to run one scenario, `--keep` to leave the built decks on disk). Free, offline, no API key needed, ~1 minute. A *recorded* model response (`tests/fixtures/*.draft.json`) goes through the real `apply_draft_to_form`; the drafted `session_state` is loaded into the real form via `AppTest`; Generate runs the real assembly. Nothing is reimplemented — the spies wrap `assembly.personalize` / `append_case_studies` / `_fill_media_plan_slide` and call through, so the assertions see exactly what the app built. **It stubs `db.log_proposal`** — until that was noticed, every run inserted a real row into the production `proposals` table, since the suite drives the app's own Generate button. The stub captures the payload instead, which is also what feeds the round-trip case. It covers the resolver (vertical from trade name, agency markup visible in the arithmetic, per-option budget tie-out to the dollar, no zero-impression or zero-cost rate line, sports priced off the ratecard rather than the Premion default, flat fee with no impressions, attribution toggles, catalog-validated audiences, non-empty and de-duplicated `unresolved`) and then the deck (no unfilled `{{TOKEN}}`s, no section dividers, one plan slide per option in consecutive order each carrying its own title, case studies contiguous and ending immediately before the first plan slide, table bottom above the Included-with-Campaign floor, zip integrity, no duplicate partnames). The HVAC scenario adds a **round trip** (`round_trip=True`, opt-in since it doubles that scenario's runtime): generate → rehydrate the logged `form_json` through the real `rehydrate_proposal_into_form` → regenerate → assert the two decks match on slide count, option count, plan titles and positions, case study count, every row's tactic/impressions/cost, totals, and unfilled tokens. Any field that doesn't survive rehydration surfaces here as a difference between the two decks, which is the only honest way to know "Load into form" actually works. **Plan slides are located by spying on `_fill_media_plan_slide`, not by matching the plan title** — with a single option the plan title *is* the proposal title, which also appears on the cover, so text matching finds two slides and the assertion fails for the wrong reason. This tier is also what catches the seed-key class of bug: it asserts the drafted rows are still costed *after* the form's first render, which is where they were previously wiped to $0.

  **Tier 2 — `! python tests/test_draft_live.py`** (`--save` writes each raw response to `tests/fixtures/*.live.json`, gitignored). Two live API calls, a few cents, run by the user. It reads the key the way the app does (`st.secrets`) and asserts **only model-layer behaviour**: a budget range with no split instruction becomes one option per stated figure, a stated rate becomes a `cpm` while "hold at rate card" leaves it absent, a trade name resolves to the right vertical, explicit exclusions ("no live sports", "no brand lift") are honoured, and `unresolved` is non-empty. (FLOW_REWORK_PLAN.md Phase 5 removed market/flight_start/flight_end from the draft schema entirely — those are band INPUTS now, never drafted, so "a year-less date resolves forward" stopped being something this tier tests; `check_common` instead proves the schema's absence, and the old date-resolution phrasing pattern being structurally gone from `unresolved`.) Assertions are structural on purpose — the model's wording varies run to run and that's fine. A failure here means the *model* drifted from what the prompt asks; re-run once before concluding anything, since a single run is a sample rather than a measurement. Tier 2's assertion logic can be sanity-checked for free by running its `check_*` functions against the recorded `.draft.json` fixtures, which is how it was validated without spending anything.

  The two tiers share the same notes fixtures (`tests/fixtures/*.txt`), so tier 1's recorded response and tier 2's live one are answers to the same question. Treat a committed `.draft.json` as frozen: edit it only to reflect a deliberate schema change, or tier 1 stops being a regression test and becomes a description of whatever the code currently does.

### A check whose expectation comes from the code under test

- **A check whose expectation comes from the same source as the code under test proves only that the code agrees with itself.** Four instances so far, and they look nothing alike until you line them up: a frozen `.draft.json` edited to match new behaviour turns tier 1 into a description of whatever the code currently does; `tests/validate_text_metrics.py` derived a line count from PowerPoint's reported row heights, which the sizer had itself set, and reported 84 disagreements that were pure artifacts; tier 1's `n_months_of()` recomputed the month count from the draft's own flight dates — the very assumption that had gone wrong — so a plan spread over three months and totalled over two passed every budget assertion it had; and a tier 2 assertion demanded a custom-audience note appear in `unresolved` while the prompt's routing rule sent it to `unresolved_internal`, so the check asserted one side of a contradiction and failed three live runs against a model that was doing the right thing throughout. **Assert against something the code can't move**: the budget the notes stated, Wide Orbit's own totals row, the rendered slide, `active_months` as the form actually holds it, what the seller sees on screen. If the only way to state the expectation is to re-run the logic being tested, there is no test — and the failure mode is silence, since a self-consistent check passes right up until someone reads the output carefully.

  **Corollary, about diagnostics.** When a value may legitimately live in more than one place — either review list, top-level `total_budget` or per-option, either of two shapes the model may return — the failure output has to print **all** of them, not just the one being searched. Otherwise a reproducible failure is indistinguishable from model drift: three tier 2 runs reported a missing note while the list it was sitting in was never displayed, which cost live API calls to learn nothing at all. `review_items()` and `budgets_in()` in tier 2 exist for exactly this, and `check_common` prints `unresolved_internal` as `[internal]` items even though no assertion reads it on its own. The rule generalises past tests: the same principle is why the deck update page reports a slide's *source* (`notes`/`anchor`/`carry`) rather than just its key.

### Read the file, not the doc — three same-day instances

- **Before moving, deleting, retiming, characterising, or reasoning about a test or a fixture, read the file — not the doc that describes it.** Docs describe intent; the file is what runs, and the two drift. Three separate instances in one day (2026-09-06/07), each producing a confidently-stated wrong answer a single `Read` would have prevented: (1) `Premion OTT.xlsx` was called "Mattress Warehouse's delivery export" throughout `ATTRIBUTION_REPORT_PLAN.md` — parsing it shows Cardinal Plumbing on every row, matching Cardinal's own attribution file instead (see "A checked-in fixture was mislabeled" above). (2) "there is no real MW delivery export in the repo" was asserted after searching for the *expected* filename rather than listing what was actually there — `MW delivery.xlsx` was sitting in the project root the whole time, carrying the exact 3.1M figure a test had just been written synthetically to stand in for. (3) `test_group_geo_resolution.py` was described as "535s of live Census calls with wild variance" and nearly moved out of the gate on that basis — reading it shows **one** network call (0.22s) with every other center short-circuited to the local crosswalk; that characterisation came from a different file's own note (`test_targeting_map.py`, since fixed).
- **The tell this rule is being broken: a claim about a file is made and the file hasn't appeared in a tool result this session.** A file's identity, cost, and behaviour are properties of the file — establish each from the file itself, before acting on any of them.

### Provenance — name the fixture a cited number came from

- **A number with no filename is a claim with no source.** WAEPA's "(13)" 0.709% was cited in a report actually built from "(14)"'s 0.13%, 2026-09-10 — the number was real, but attributed to the wrong sibling document. A citation has to name which file it came from AND confirm that file is the one actually in use this session, not just a plausible-looking match. Distinct from "read the file" above: that rule is about a claim going stale against the file itself; this one is about a claim being unsourced even when accurate — the file can be read correctly and the number still get attributed to the wrong document.

### A frozen fixture's date rots against the wall clock — found and removed 2026-09-09

- **The file: `tests/test_draft_regression.py`, `check_draft_state`, the "flight start is not in the past" assertion, HVAC scenario.** The drift: `tests/fixtures/hvac_two_option.draft.json` carries a frozen `flight_start` of `2026-09-08` — a real date the model actually returned back when this fixture was recorded, before FLOW_REWORK_PLAN.md Phase 5 removed `flight_start`/`flight_end` from the draft schema entirely. The assertion compared that frozen literal against `date.today()`, which had crossed 2026-09-08 by 2026-09-09 — a fixture created once, checked forever against a clock that never stops.
- **Not a flake and not really "in the past" — this check had already stopped meaning anything, and the date crossing was just when someone noticed.** `apply_draft_to_form` never writes `flight_start`/`flight_end` — Phase 5 made market/flight band INPUTS the app reads FROM session_state, not drafted outputs (`current_start = st.session_state.get("flight_start") or DEFAULT_FLIGHT_START`, its own comment says so). The suite's `band_preset_from(draft)` helper only reuses each frozen fixture's leftover flight fields as a convenient stand-in for "what the band already had" before applying the draft — a testing-harness choice, not app behavior. So the assertion was never testing "does a year-less date resolve forward" (the feature it was originally written for, and which no longer exists — tier 2's own `check_common` proves the schema's absence instead, see the tier 2 entry above); it was testing "is this hardcoded test literal still in the future," which is not a property of the app at all.
- **Every other scenario fixture carries the identical time bomb, just further out** — `ashford_post_draft.draft.json` (2027-01-04), `dental_single_option.draft.json` (2027-01-01), `custom_audience_cap.draft.json` (2027-03-01). Deferring this to BACKLOG rather than fixing it would only postpone today's HVAC failure to whichever of those three comes due next — the trigger condition is "time passes," which isn't a condition worth tracking, it's a certainty.
- **Fix: the assertion was deleted, not adjusted.** No replacement value (a later fixed date, a relative offset) would do anything but move the same expiration further out, since the underlying property it checked doesn't exist in the app anymore. The neighboring "flight end follows flight start" check (a real, timeless structural check on the band preset's own two dates) stays. Same family as "A check whose expectation comes from the code under test" above, from a different angle: that entry is about an expectation DERIVED from the code under test; this one is about an expectation that was true when WRITTEN and is guaranteed to become false as real time passes, regardless of what the code does — recognizable by any assertion comparing a frozen fixture value against `date.today()`/`datetime.now()`.

### A test asserting against a mutable Supabase-hosted asset rots the same way a frozen date does — found and fixed 2026-09-23

- **Two files, one shape: `test_targeting_map.py`'s "the targeting slide carries exactly the map picture" and `test_standalone_avails_builder.py`'s "the map variant was used automatically (one placed map picture, no native stock photo)" both asserted a TOTAL PICTURE COUNT on the map-variant avails/targeting slide, and both had been silently, consistently red — misdiagnosed as the pre-existing, genuinely-nondeterministic BACKLOG.md flake ("sometimes 1 picture, not 3") they happened to resemble on the surface.** Checked directly before assuming: run the same file three times in a row, byte-identical failure every time (`['Picture 4', 'Picture 82']`) — not flaky at all, a real, 100%-reproducible defect in what the assertion expected.
- **Root cause, traced by bisection, not guessed:** the ACTIVE Supabase deck version had changed that same day — `deck_versions` id 9, `TEGNA_MASTER_DECK_9-23-26.pptx`, uploaded 2026-09-23, notes **"Background change for avails"** — a real, legitimate template edit made independently of any code in flight. The new version bakes a full-slide dark-gradient **picture** onto the map-variant slide (`Picture 4`, position `(0,0)`, full slide dimensions) where the template used to rely on a plain PowerPoint `<a:gradFill>` background (confirmed: the checked-in local fallback `TEGNA_MASTER_DECK_v1_1.pptx` still has zero pictures on that same slide — a different, older file, different SHA256, different slide count). Two pictures on that slide (the new background + the map `place_targeting_map` adds) is now the CORRECT count under the new template; the tests' "exactly 1" assumption was simply never updated for it.
- **The general lesson, not just this instance: an assertion against a Supabase-hosted asset's CONTENT (not just its presence) rots the moment someone edits that asset, the same way a frozen wall-clock date rots the moment real time passes it** — see the entry directly above. Neither is a code regression; both are an assumption about something outside the code's control that was true when written and had no mechanism forcing it to stay true. The fix in both cases is the same shape too: stop asserting the thing that's free to drift (a total picture count; a specific future date) and assert the thing that actually matters and can't drift with it.
- **Fix: identify the MAP picture specifically, not the slide's total picture count.** `test_targeting_map.py` compares each picture's raw bytes against the SAME `map_png` this proposal's own `fill_data` computed (`place_targeting_map` embeds a PNG verbatim — python-pptx doesn't re-encode one it's simply handed — so a byte-exact match is unambiguous and needs no assumption about size). `test_standalone_avails_builder.py` matches by the map's own known render dimensions instead (`(1000, 620)`, that test's own `render_map` call), since it doesn't have a captured `fill_data` to compare bytes against. Both now assert "exactly one picture matches the map, however many OTHER (background) pictures the template carries" — immune to the next time anyone edits that background again. BACKLOG.md's old "sometimes 1 picture, not 3" entry (2026-08-28, the pre-map-variant-slide overlay design) is marked CLOSED — superseded by the map-variant redesign before it was ever root-caused, and unrelated to this incident. Guards: both files themselves, now passing (105 and 20 checks respectively), re-run 3× clean.

## Planning

### A redirected item can go stale silently — the rationale that moved it is never re-verified against the code that ships after it

- **The shape, generalized from the Campaign Specs incident (2026-09-04):** a planning note redirects a queued change into a later phase, citing a real-sounding technical reason ("Geography's autofill now depends on markets the AVAIL resolves, not on Section A's picker directly"). That later phase ships, but narrower than planned — the redirected item isn't part of what actually lands. Nobody closes the loop: the item sits marked "still open" in the plan document, and the REASON it was redirected sits right next to it, never re-checked against whatever the code looked like by the time anyone next asked about the item. Months later, someone asks a fresh question about it — and the stale rationale is still the only answer on file, presented (by anyone reading it, including an assistant) as settled fact rather than as an unverified claim from a prior state of the code.
- **What made this one findable rather than just repeated:** the interface audit that surfaced it didn't accept the plan document's own claim — it traced `apply_geography_autofill`'s actual call site, read its own comment (which already said the value is read from session_state precisely *because* it doesn't need the thing it was supposedly waiting on), and then verified live against a real avails import that resolved seven geographies without any of them reaching the field in question. The plan document was internally consistent and wrong; only checking it against the running code caught that.
- **The general rule this is worth naming, not just this one instance:** an "open" item's own stated blocker is a claim with a timestamp, not a fact — it was true (or believed true) when someone wrote it, against the code as it existed then. Code keeps moving after a plan note is written; the note doesn't. Before treating a redirected/deferred/"still open" item's own rationale as current, check it against the code that exists **now** the same way any other claim about the codebase gets checked — not against what the plan document asserts about why it was set aside. The cost of skipping this is exactly what happened here: a genuinely simple move (a few lines of reordering) sat undone for a full phase-and-a-half because the reason it couldn't happen yet was never re-asked.
- **Trigger to apply this:** any time a plan document, a CLAUDE.md status line, or this file itself describes something as blocked, deferred, or "not yet" — and someone is about to make a decision that depends on that being still true.

## Attribution Report Builder

### `report_assembly.py`/`report_charts.py` reuse existing modules rather than adding new ones

- **`report_assembly.py` imports `assembly.py`'s private fill primitives (`fill_bullet_list`, `clone_table_row`, `_replace_tokens_in_text_frame`, `_tighten_cell_paragraphs`, `_find_shape_by_name`, `delete_slide`) rather than re-implementing the same XML-cloning logic a second time.** `assembly.py` is a pure python-pptx module with no Streamlit dependency, so importing it from a second, unrelated deck-assembly module carries no extra weight — the underscore prefix on those names is Python's usual "not part of the public surface," not a real boundary. The one place this couldn't just reuse `assembly.fill_table_rows` outright: that function finds "the first table on the slide" (`_find_table_shape`), which breaks the moment a slide carries two tables — the Delivery Recap slide has both `TopPublishersTable` and `CreativeTable`. `report_assembly._fill_named_table` is the by-name equivalent, built on the same row-cloning primitive.
- **`report_charts.py` uses Pillow, not matplotlib, for its bar chart.** matplotlib isn't in `requirements.txt` and isn't installed — pulling it in for one chart function would be a new pinned dependency added without discussion, against this project's own established preference (`targeting_map.py`'s map rendering already chose "Pillow alone, no filesystem font lookup" for exactly this kind of image). Rewritten as a plain `ImageDraw` horizontal-bar renderer using `ImageFont.load_default(size=N)`, the same font call `targeting_map._legend_font`/`_place_font` already use.

### The report deck template had no row-height/text-fit measurement pass — real fix landed 2026-09-06

- **Confirmed by rendering, not assumed:** `REPORT_MASTER_v0_2.pptx`'s Delivery Recap slide gives `TopPublishersTable` and `CreativeTable` roughly 1.6-1.8in each (measured directly: `TopPublishersTable` top=3.75in, `CreativeTable` top=5.40in, slide bottom 7.5in). The full list moves to the recap's `AUDIENCE_BULLETS` as its own line (`geography_overflow_bullet`) instead of being lost. Re-rendered against the real 4-market MW fixture: the tile reads "4 markets" (fits cleanly), and the Audience card gains a "Markets: Raleigh-Durham (Fayetville), Greensboro-H.Point-W.Salem, Roanoke-Lynchburg, Charlotte" bullet.

### Stubbing a function that is someone else's DEFAULT ARGUMENT is a silent no-op

- **The shape, worth recognising anywhere it recurs:** `geo_resolver.radius_to_zips(centers, miles, geocoder=geocode_address)` binds `geocode_address` **at function-definition time**, so the default parameter holds a reference to the original function object forever. Monkeypatching `geo_resolver.geocode_address = stub` afterwards rebinds the *module attribute* and changes nothing about what `radius_to_zips` actually calls — the patch appears to apply, the test passes, and the live network call happens anyway. Nothing raises; nothing looks wrong; the stub is simply never consulted.
- **Where this bit:** taking the last live network call out of the gate (2026-09-07). `test_group_geo_resolution.py` feeds a deliberately bogus address to the real Census Geocoder through the form, via AppTest, so there is no call site to pass `geocoder=` into. The obvious patch (`geo_resolver.geocode_address = lambda _: None`) would have left the network call fully live while reading, in the diff, exactly like a working stub.
- **The fix, and the general rule:** replace the *module attribute the caller looks up at call time* — here `geo_resolver.radius_to_zips` itself, wrapped so it forwards to the real implementation with `geocoder=` supplied — rather than the name that was captured into a default. `app.py` calls `geo_resolver.radius_to_zips(...)`, an attribute lookup performed on every call, so the wrapper reaches code running inside AppTest. **Before stubbing anything, check whether the name is captured in a default argument, a decorator, a class attribute, or an `from x import y` alias in the consuming module — all four freeze the reference at import/definition time and make an attribute-level patch a no-op.** Patch the thing that is looked up when the call happens.
- Guard: the stub's own comment block in `tests/test_group_geo_resolution.py` states this, and both bad-address assertions still pass (they assert the address is reported unresolved BY NAME, which the stub reproduces exactly, since the real geocoder also returns None for it).

### Recursive Douglas-Peucker overflows on real ZCTA rings

- **`build_zcta_boundaries.simplify` is iterative (explicit stack), not recursive, and must stay that way.** A real ZCTA ring carries thousands of vertices, and the textbook recursive form blows Python's stack on the worst of them. **Raising `sys.setrecursionlimit` does not fix it -- it relocates the crash from a catchable `RecursionError` to a C-level stack overflow, which cannot be caught and takes the whole interpreter down.** The iterative form is the same algorithm with the recursion made explicit, and has no depth limit worth worrying about.

### The facts-only checker approximates in both directions

- **Three findings, not two, are the same shape read from a few different sides: the facts-only checker (`app._attr_payload_numbers`/`_attr_draft_number_violations`, Phase 4) recognizes a fixed set of number SHAPES a real fact can appear in — plain/comma-formatted integers, 0/1/2-decimal percentages for anything rate/share-like, K/M/B-abbreviated magnitudes, list lengths — and every failure below was the checker's own coverage running out, not a fabrication it should have caught (2026-09-08, 2026-09-12) or a legitimate fact it should have passed (2026-09-09).**
- **The miss (2026-09-08, Cardinal, live): the checker let a fabricated number through.** The model wrote "roughly 1 in 15" by inverting a SUM of two real, separately-listed facts (4.7% + 1.9% ≈ 1-in-15) — genuine new arithmetic the facts-only contract exists to forbid. The check missed it because "15" happened to also be a real, unrelated fact sitting elsewhere in the same payload — a coincidental string collision, not a gap in which shapes the collector walks. **This class of miss is structural, not closeable by adding another shape**: the checker verifies every emitted number traces to SOMETHING in the payload; it cannot verify that a traced number wasn't REACHED by arithmetic performed on other traced numbers, since that would mean re-deriving every ratio the model states — a different, much larger checker. The prompt's own facts-only paragraph now names this exact pattern as a worked counter-example (`app.build_attr_draft_prompt`), which lowers the odds of recurrence and does not close the class.
- **A second miss of the identical shape (2026-09-12, Cardinal, live, found in the Highlights/Takeaways rework's own re-read): the checker let fabricated CONTENT through, not just fabricated arithmetic, because the content happened to be numeric.** A drafted highlight described "the Offers page — likely tied to the $49 Heating Tune-Up and 65% off sink promotions." Nothing in the facts payload names any promotion — `_bucket_url` (`report_assembly.py`) derives a page's label mechanically from its URL path segment (e.g. "Offers"); the model has no visibility into what a page actually advertises and invented both the tune-up price and the discount percentage. The checker missed both numbers because "49" and "65" each happened to coincidentally match unrelated real figures sitting elsewhere in the same payload — the exact "1 in 15" collision shape, just fabricating a plausible-sounding CLAIM instead of a plausible-sounding RATIO. Fixed the same way as the first instance: not a new checker shape (there is no numeric pattern that distinguishes "a real fact stated as a number" from "an invented fact that happens to be numeric"), but a prompt-level contract naming the boundary explicitly — the model has no information about a page's content beyond its category label and visit counts, stated as its own rule alongside the numeric facts-only contract (`app.build_attr_draft_prompt`). Guard: verified by re-drafting Cardinal live after the fix — the rebuilt highlight reads "the Offers page drew 6% of attributed visitors," label and number only.
- **The false positive (2026-09-09, WAEPA, live, found building Phase 5): the checker flagged a legitimate number it had never learned to recognize.** Phase 5 added `facts["budget"]["cost_per_attributed_visit"]`/`["cost_per_conversion"]` — the first dollar-and-cents facts this payload ever carried (`121.1147...`, neither a plain integer nor a 0-1 rate/share). A live WAEPA draft correctly wrote "$121.11," the exact right number, and the check flagged it as unfaced anyway, because "121.11" traced to no shape `_attr_payload_numbers` had ever registered. Fixed by having `add_int` also register a non-integral value's own `.2f`/`.1f` string forms (`app.py`, alongside the K/M/B fix this is the same shape of gap). Re-verified live after the fix: the identical draft, re-run, passed with zero violations.
- **The conclusion both incidents point to, and the one worth keeping: this checker approximates the facts-only contract, in both directions, by design — it cannot be a complete formal verifier of "is this number real" without becoming the size of a second drafting pipeline.** It closes the common cases (fabricated sums, fabricated inversions of round numbers, a genuinely wrong figure) and it will keep needing new shapes registered as the payload grows new kinds of real facts (Phase 5's dollar-and-cents figures were the first; the next will be something else). **The real backstop is a rep reading the narrative before it ships, not the checker catching everything** — which is also why `apply_attr_draft` silently discarding the model's own `goal_alignment_notes` (found and fixed alongside the "1 in 15" incident) mattered more than either of these two findings: a rep who never sees a flagged disagreement can't apply the backstop the checker was always going to need.

### "Day of Week" is exactly what it says — Phase 1's own finding was wrong, and a sum check would have caught it (2026-09-10 correction)

- **Phase 1 (gotcha 2) classified every 1-day-gap, 7-row date-headed tab as "a trailing daily window... confirmed against two real exports it is NOT a weekday aggregate, just the most recent several calendar days."** That finding was never checked against a sum, and the sum is decisive: across all three real fixtures on hand -- WAEPA, MW, Cardinal -- the 7 rows of the tab literally named "ATTRIBUTED RATE BY DAY OF WEEK" sum to the export's own headline `delivered_impressions` to the LAST impression (WAEPA: 2,220,083 both ways; MW: 2,341,223 both ways; Cardinal: 917,450 both ways). A genuine trailing window of the most recent several calendar days could never do that -- there is no mechanism by which "the last 7 days pulled" would sum to exactly the whole flight's total. It is the Day of Week aggregate, named accurately by Premion's own dashboard; the "trailing window" story was a misreading Phase 1 never verified.
- **The tab's own dates are LABELS, not real dates -- a second thing Phase 1 got wrong by extension.** A real WAEPA pull (14) labeled its 7 rows Sep 9-15, 2026, though the campaign it describes ran March 30 - June 29, 2026. The dashboard always stamps this tab with one fixed reference calendar week regardless of when the actual flight ran; the fix reads each label's real weekday via `date.weekday()` (Sep 9, 2026 is a Wednesday, so the seven labels map Wed/Thu/Fri/Sat/Sun/Mon/Tue) rather than trusting the date's own calendar position for anything.
- **All three real fixtures also confirm the flip side: none of them has a genuine trailing-daily tab at all.** Checked directly -- every date-headed tab across WAEPA/MW/Cardinal is either this 7-row weekday aggregate or the real weekly trend (7-day gaps, correctly classified all along). `daily_trend` (kept as a field, for a shape that isn't ruled out but has never been confirmed to exist) is empty on every real export on hand; it was silently holding the mislabeled Day of Week data the whole time this project has run, since nothing downstream ever actually consumed `daily_trend` to notice.
- **The fix leans on the sum, not just the row count, per the same discipline this project already applies to test expectations ("assert against something the code can't move").** `_classify_date_series` now takes the candidate's own row sum and the export's headline total; a 1-day-gap tab is `"day_of_week"` only when the sum matches, and falls back to the old `"daily"` bucket otherwise -- so a differently-shaped 1-day-gap tab (still unconfirmed to exist) is never misread as a weekday aggregate it isn't, the same caution the correction itself is a case study in. `attribution_import.py`'s own module docstring (gotcha 2) carries the full corrected story now.
- **Consequences, all applied same-day:** the optimization engine's weekday dimension (`ATTRIBUTION_REPORT_PLAN.md`'s deferred list) is unblocked -- it IS derivable, and MW's own real Wednesday delivery cut (143,062 impressions against 277K-451K every other weekday) is now visible in `by_day_of_week` and independently confirms the fix reads real, externally-verifiable client behavior, not just an internally-consistent number. No other tab in the parser is classified by date-gap heuristics (checked directly -- the delivery export's own daypart tab is identified by its own distinct header, `"daypart distribution"`, never by gaps), so this was the only place the same mistake could have been hiding.
- **The lesson, stated plainly because Matt's own words earned it: "the sum check would have caught this in Phase 1."** A one-line arithmetic assertion (`sum(row.delivered_impressions...) == export.delivered_impressions`) sat unwritten for the life of this feature while the tab's own name said exactly what it was. Read literally against what a tab is NAMED, and check what its own numbers reduce to, before writing a story about why the name must be wrong.

### Phase 5's own acceptance walkthrough (2026-09-10, Matt) found two real bugs the deck-level checks couldn't — and a standing rule came out of it

- **Both new checks (goals prefill, the proposal picker's own content) were verified against `report_assembly.py`'s output and against the pre-linked door only — never against the page's OTHER door into the same state.** `render_attribution_reports_page` has always had two ways to end up with a linked proposal: the pre-linked door (`prelinked_row`, set by Proposal History's "Build report" button) and the in-page search-and-pick door (section 3's own radio + Confirm, setting `attr_proposal_id` directly). The fix is a single unification: `linked_row` resolves from `prelinked_row` OR, when that's absent, a fresh `db.fetch_proposal(attr_proposal_id)` — computed once, at the top of the function, exactly like `prelinked_row` already was, and used everywhere `lf`/the goals-audience prefill/the post-link caption read from. The Phase 5 tests that existed before this (`check_phase5_proposal_link` in both `test_report_assembly.py` and `test_attribution_reports_page.py`) only ever drove the pre-linked door — a curated-scenario gap of exactly the shape CLAUDE.md's own "find affected files by grep, not recollection" rule warns about, just for TEST COVERAGE rather than a code change: driving one door and calling the feature verified is the same mistake as fixing one call site and calling a rename done.
- **The proposal picker showed only a bare client name and match score** ("WAEPA (score 1.00)") — useless the moment a client has more than one proposal, which is the exact case a picker exists for. `_proposal_candidate_label(candidate, row)` now builds each radio option from the candidate's own full `db.fetch_proposals()` row: title, flight dates (from `resolve_setup`, never the free-text `flight.label`), when it was logged, and who logged it — matching the picker candidate's own `resolve_setup`-derived dates rather than a display label was itself a small test-fixture bug found building the test for this (a `flight_label=` fixture kwarg only ever fed `form_json["flight"]["label"]`, never `form_json["setup"]["flight_start"/"flight_end"]`, which is what the picker actually reads — the SAME structured-data-over-narrative-text principle `geo_column_default`'s 2026-09-08 fix already established, just tripped in a test fixture instead of app code this time).
- **Real gotcha, found writing the tests for this: `app.call_claude_attr_draft = stub` does not intercept the call `render_attribution_reports_page` makes when the page is driven through `AppTest.from_file(...)`.** Confirmed directly — a stub instance sitting in `app.__dict__["call_claude_attr_draft"]`, verified still there by identity after the run, was never invoked; a real, billed API call happened instead (visible in the `[claude] {...}` log line, with a real `request_id`). `AppTest.from_file` re-executes app.py's own source into its own script-run context; a bare-name call to a function DEFINED directly in app.py resolves against THAT execution's own globals dict, not the separately-`import app`-ed module object a test file holds a reference to and mutates. `db.*` stubbing throughout this same test file works fine for the opposite reason: `db` is cached in `sys.modules`, shared and identical regardless of how many times app.py's own script body gets re-executed, so mutating `db`'s attributes from outside reaches every execution of `import db` anywhere in the process. A function living directly in app.py has no such shared home — **this is a sibling of "stubbing a function that is someone else's default argument is a silent no-op"** (this file, above), just triggered by AppTest's re-exec model instead of a captured default parameter, and worth recognizing by the same tell: a stub that's provably still in place (checked by identity) and still never runs. It is also exactly why `test_draft_regression.py` (Tier 1) has never clicked a live-call button through AppTest at all — it calls `apply_draft_to_form` directly and injects the result into `session_state`, sidestepping the whole class of problem. The fix here follows the same shape: `tests/test_attribution_reports_page.py`'s `_ATTR_STUB_DRAFT` (an empty dict) is pre-seeded into `at.session_state["attr_draft"]` before every Generate click that doesn't care about drafted CONTENT, so the self-sufficient auto-draft branch (below) sees a non-None draft and never fires the live call at all — free, deterministic, and it exercises the REAL "already have a draft, use it as-is" code path rather than a fake one.
- **The UX redesign (folding "Log this report" into Generate; renaming "Draft narrative" to "Preview narrative" and making it optional; Generate drafting automatically when nothing's been previewed) is what actually needed the stub fix above** — before this redesign, Generate never called the network on its own; after it, EVERY Generate click without a prior preview does, which would have made this file's routine, free AppTest suite start spending real money on every run without the pre-seeding fix. `apply_attr_draft`'s own returned `draft_warnings` already folds in every `goal_alignment_notes` entry (its own docstring says so) — a first pass at the self-sufficient Generate path also warned the freshly-auto-drafted notes explicitly, right before `apply_attr_draft` warned them again, printing every alignment note twice. Found live, in the browser, walking the real page with the real WAEPA pair after the redesign shipped (not by a test) — fixed by dropping the redundant explicit loop and letting `apply_attr_draft`'s own pass be the only one that warns.
- **The new standing rule this produced (CLAUDE.md, alongside "look at the pictures"): walk the page as a rep, in a browser or AppTest at minimum, before declaring a flow change done — a green test and a correct deck are not evidence the page between them works.** Two of this pass's real bugs (the search-and-pick prefill gap, the bare-name picker) were invisible to the existing deck-level and pre-linked-door tests and were only found because Matt clicked through the actual page in the order a rep would; the duplicate-warning bug was caught the same way, in this session's OWN follow-up browser walkthrough, immediately after fixing the first two — which is itself the rule's own justification demonstrated in real time: the fix for bugs 1 and 2 shipped a third bug that no test (existing or newly written) happened to exercise, and only rendering the actual page surfaced it.

### v0_6 fill code, and a second live-test file that was quietly spending real API money on every sweep

- **`report:response_profile` became a REQUIRED slide, not an optional one, on purpose.** Every other new attribution-report slide (`report:live_sports`, and now `report:ott_retargeting`) was made optional because the underlying DATA is optional — a delivery file might carry no sports block, an OTT retargeting export might never be uploaded. Recency/referral data comes from the SAME Website Attribution export every report already requires, so there is no real-world case where a report has an attribution export but no response-profile facts; making the slide optional would have meant writing dead conditional logic for a case that can't happen. The cost is real and accepted: any template older than v0_6 (v0_4 and earlier, still sitting in the repo root and in old `report_deck_versions` rows for "Rebuild as presented"-style reproduction) now fails `build_report_deck` outright rather than silently omitting the slide — the same trade-off `report:recap`/`report:highlights` etc. already made when THEY became required.
- **A second, real, pre-existing bug, found rendering the very first no-delivery build against v0_6: `report:live_sports` was left in the deck completely unfilled whenever `delivery is None`.** `build_report_deck`'s `drop_keys` computation had two branches — `if delivery is None: drop_keys = [...]` (a hardcoded list) and `else: ... if not live_sports_applies(delivery): drop_keys.append("report:live_sports")`. The hardcoded branch never included `report:live_sports`, so a report built with NO delivery file at all (WAEPA's own real shape) left the slide sitting in the output with every `{{SPORTS_...}}` token still literal — invisible to every deck-level check written before this, because none of them happened to build a no-delivery WAEPA deck against a template that HAD the slide (v0_4, the template every prior WAEPA check used, doesn't carry `report:live_sports` at all — the slide didn't exist yet when those checks were written, so there was nothing to leave unfilled). Only visible once v0_6 — the first template new enough to carry the slide — was built against WAEPA's own real no-delivery shape, and only because the render was actually looked at (a screenshot, not just a token-scan) before being sent out.
- **The first fix (add `"report:live_sports"` to the hardcoded list) patched the symptom and left the actual shape in place — Matt caught it: "any list of slide keys that exists in two places is stale the moment the first one grows."** Two independently-hardcoded lists is the bug, not which key was missing from one of them; patching the missing key leaves a THIRD delivery-set slide one day away from the identical miss. The real fix collapses both branches into one: `delivery_breakdown_applies`/`live_sports_applies` already treat `delivery is None` as "doesn't apply" (checked directly — both have always handled it), so a single `delivery_set_applies` dict (key → applicability function, `report:delivery_recap`'s own entry a bare `lambda d: d is not None`) replaces the two branches outright — `drop_keys = [key for key, applies in delivery_set_applies.items() if not applies(delivery)]`, called once, uniformly, whatever `delivery` is. A fourth delivery-set slide now needs exactly one new dict entry, never two lists kept in sync by memory. The general lesson, worth naming past this one bug: **whenever the same list of keys would otherwise have to be written twice — once for a "nothing" case and once for a "something" case — that's a sign the "nothing" case should be expressed as every item's own applicability function returning false, not as a second, separately-maintained list.**
- **`test_attribution_draft_live.py` was never added to `run_all.py`'s live-test exclusion, the third time this exact class of miss has happened — and the third time was the one that changed the mechanism, not just the list.** `test_draft_live.py` and `test_categorize_live.py` both earned a spot in the old hand-maintained `EXCLUDED_BY_DEFAULT` dict only after someone noticed a routine sweep spending real API money on a probabilistic check; the Attribution Report Builder's OWN Tier 2 (`ATTRIBUTION_REPORT_PLAN.md` Phase 4/WAEPA) was built afterward and nobody carried the pattern forward into that dict a third time. Found the same way both prior instances were found: a routine full sweep failed on "[Cardinal monthly -- service calls] a highlight bullet cites the lead-intent fact," and a manual re-run of the identical file against identical code, minutes earlier, had already passed cleanly (26/26) — the signature of drift, not a regression, per the file's own documented warning ("re-run once before concluding anything"). **First fixed the same way both times before (added to the dict); Matt's own ruling closed the class instead of patching the third instance of it: "make it a rule... the convention is the protection, not memory."** `tests/run_all.py` now excludes any `test_*_live.py` file by NAME alone (`is_live_by_name`, a suffix regex), with `EXCLUDED_BY_DEFAULT` demoted to the documented escape hatch for a live test that doesn't follow that suffix (none exist today) — a fourth `*_live.py` file needs no entry anywhere to be excluded.
